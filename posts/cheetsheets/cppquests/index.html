语言基础#

strlen和sizeof#

  • sizeof：在编译期计算对象或类型所占字节数，对数组返回整个缓冲区大小，对指针返回指针本身大小，时间复杂度为 O(1)。
  • strlen：在运行期遍历字符直到遇到’\0’，返回 C 风格字符串长度（不含终止符），时间复杂度为 O(N)。

现代C++中，更加推荐使用stl，比如array或者vector

内联函数是什么，有什么好处和坏处？#

**内联函数（inline）**是对函数的一种编译期建议，告诉编译器“在每个调用点直接展开函数体”，而不是做一次真正的函数调用。

好处在于：

  1. 消除调用开销：避免栈帧、参数拷贝和跳转开销，提升执行效率。
  2. 优化机会更多：展开后，编译器能做常量传播、死代码消除、循环展开等跨调用优化。
  3. 头文件定义安全：同一份 inline 函数可在多个翻译单元中定义而不违背 ODR（One‑Definition Rule）。

坏处在于：

  1. 代码膨胀：多处展开会增加可执行文件体积，可能影响 I‑cache 表现。
  2. 编译时间变长：更多展开和跨调用优化，加重编译负担。
  3. 展开不可控：编译器可根据函数体大小或递归等原则忽略 inline 建议。
  4. 调试不便：调用栈中看不到函数边界，单步调试和性能剖析不够清晰。

explicit作用#

  • explicit：用于修饰单参数或多参数（带默认值）构造函数，禁止其进行隐式类型转换。

final作用#

  • final：用于修饰虚函数或类，禁止虚函数在派生类中被覆写或禁止类被继承，提高设计安全性。

四种类型转换#

  • static_cast：编译期类型转换，适用于已知安全转换（如基类↔派生类指针/引用、数值类型之间）时使用。
  • dynamic_cast：运行期安全向下转型，用于多态类层次，通过 RTTI 检查转换是否合法，失败时返回nullptr或抛出异常。
  • const_cast：添加或移除对象的const/volatile限定，用于调用需要非常量接口或暂时去除常量属性。
  • reinterpret_cast：最低安全级别的强制转换，用于不同类型之间的按位重解释（如指针与整数互转、不同指针类型互转），须谨慎使用。

命名空间#

  • 命名空间用于防止名称冲突并对代码进行逻辑分组，可以使用namespace 名称 { … }定义，在需要时通过using声明或限定名来访问其中的标识符。

函数指针#

  • 函数指针是一个存储函数地址的指针变量，可以用于动态调用不同函数，实现回调和策略模式等。定义形式为返回类型 (*指针名)(参数类型列表)，使用时可通过该指针调用对应签名的函数。

  • 函数指针本质是指向函数的指针，它保存了一个函数的入口地址，可以在运行时将不同函数赋值给同一个指针变量，并通过该指针进行调用。

  • 典型用途包括：

    • 回调函数：当库或框架需要用户提供行为时，将函数指针作为回调参数传入。
    • 策略模式：通过将不同的逻辑函数赋给函数指针，实现运行时选择算法或操作。
    • 函数指针数组：管理一组同签名的函数，根据索引或条件灵活调用。
    • 动态链接：从共享库（.so/.dll）中获取函数地址后，用函数指针调用。

  • 例如，声明一个指向接收两个int返回int函数的指针：

静态局部变量、全局变量、局部变量的区别和使用场景#

  • 局部变量：在函数或代码块中定义，具有自动存储期，调用结束后销毁。
  • 静态局部变量：在函数内部定义但加static，具有静态存储期，只初始化一次，并在多次调用间保留值。
  • 全局变量：在函数外部定义，具有静态存储期且对整个程序可见，可用于跨函数共享数据。

使用场景:

  • 静态局部变量：

    • 统计函数被调用次数，如static int count；

    • 缓存函数内部计算结果以便下次直接使用；

    • 需要在函数内部维护状态但不希望暴露为全局变量。

  • 全局变量：

    • 程序启动时需要初始化的全局配置；
    • 多个函数间需要共享状态且生命周期贯穿整个程序，例如日志级别、单例对象指针等；
    • 需要与外部模块或库进行全局通信时，可将其放在全局命名空间。

C++ 中 new 和 malloc 的区别？delete 和 free 的区别？#

  • new：在 C++ 中分配并构造对象，返回适当类型的指针。
  • malloc：在 C/C++ 中分配原始内存，不调用构造函数，仅返回void*。
  • delete：在 C++ 中销毁对象并释放内存，调用析构函数。
  • free：在 C/C++ 中仅释放内存，不调用析构函数。

返回值优化#

返回值优化（RVO）和命名返回值优化（NRVO） 是编译器在返回局部对象或临时对象时省略拷贝/移动，在调用者栈上直接构造对象，从而提升性能；在 C++17 起，类类型的返回值拷贝已被保证省略。

RVO（Return Value Optimization） 函数直接返回一个临时对象：

Widget makeWidget() {
  return Widget(42);  // 临时 Widget，将直接在调用者的返回值空间构造，无拷贝
}

NRVO（Named Return Value Optimization） 函数返回一个具名局部变量：

1

3
4

Widget makeWidget() {
  Widget w(42);
  return w;  // w 直接在调用者空间构造，无拷贝
}

编译器如何实现函数重载？参数如何匹配？#

实现机制——Name Mangling：编译器将函数名 + 参数类型编码为唯一符号（如 _Z3fooi 表示 foo(int)）。返回值不参与编码，因此仅返回值不同无法构成重载。

参数匹配——重载决议（编译期），分三步：

  1. 构建候选集：名字相同且可见的函数（含 ADL 查找）
  2. 筛选可行函数：参数数量匹配且每个参数可隐式转换
  3. 选最优匹配：按转换优先级排名
优先级 转换类型 示例
① 精确匹配 int → int
② 类型提升 char → int
③ 标准转换 int → double
④ 用户定义转换 构造函数/operator

若无唯一最优解则产生二义性编译错误。

函数默认参数是什么？背后原理？#

默认参数允许调用时省略末尾参数，由编译器在调用处自动补全。

原理：编译器读取声明处的默认值，在调用点展开为完整参数，运行时无任何额外机制，默认值信息仅存于编译器符号表，不进入目标代码。

核心规则：

  • 只能从右向左省略，不能跳过参数
  • 默认值写在声明处（头文件），定义处不写
  • 默认值可以是运行时表达式/全局变量（每次调用时求值，非编译期常量）

虚函数陷阱：动态分派（运行时）决定调哪个函数，默认参数填充（编译期）按静态类型决定。结果是调用了派生类函数却用了基类的默认值，应避免在虚函数中使用默认参数。

  1. 什么是 union
  • 定义：union（联合体）是一种特殊的类类型，它的所有成员共用同一段内存。

    • 所有成员起始地址相同。
    • union 的大小等于最大成员的大小（可能再加上对齐填充）。

    3. 协议解析：比如网络包头可能有不同格式，可以用 union 叠加在同一内存上。

（4）struct vs union 的区别？

  • struct：所有成员独立存储，大小是所有成员大小之和（再加上对齐）。
  • union：所有成员共用存储，大小是最大成员大小。

内存模型和指针/引用#

内存对齐#

一、什么是内存对齐

  • 对齐(Alignment)：在内存中，某种数据类型的对象地址必须是该类型对齐值（alignment requirement）的整数倍，否则 CPU 访问该对象可能要做额外的总线周期，甚至在一些架构上会报硬件异常。
  • 对齐值的由来：通常与类型的大小相关，例如在大多数 64-bit 平台上，double 的对齐值为 8，int 的对齐值为 4；这叫做 自然对齐(natural alignment)。
  • 结构体内对齐：编译器会按照各成员的对齐值来排列成员，并在必要时插入填充(padding)，以保证每个成员都从合适的地址开始；整个结构体的大小也会向最大成员对齐值取整。

二、对齐相关的关键概念

  1. alignof(T)：编译时运算符，返回类型 T 的对齐值。
  2. 自然对齐：成员按照自身大小或平台要求对齐。
  3. 最大对齐：std::max_align_t 表示平台上最严格的对齐要求，默认 new、malloc 会返回满足此对齐的内存。
  4. 自定义对齐：可以指定比自然对齐更严格（或更松）的对齐策略。

三、C++ 中如何控制对齐

方式 用法示例 备注
alignas（C++11 起） cpp<br>struct alignas(16) Vec { float x,y,z,w; }; 编译时指定类型或变量的对齐值，最优先级最高
alignof cpp<br>static_assert(alignof(Vec)==16); 获取类型的对齐值
GNU/Clang 属性 aligned cpp<br>struct __attribute__((aligned(32))) BigBuf { char buf[64]; }; 与 alignas 等价，但是编译器扩展
MSVC 特性 __declspec(align) cpp<br>__declspec(align(32)) struct BigBuf { char buf[64]; }; 与 alignas 等价，但针对 MSVC
#pragma pack #pragma pack(push,1) struct Packed { char a; int b; };#pragma pack(pop) 修改后续结构体的对齐方式（此例强制每个成员 1 字节对齐，去掉 padding）

四、分配对齐内存的方法

  • 默认分配
    • new T / malloc 保证返回的内存满足 std::max_align_t 对齐，可安全存放任何类型。
  • C++17 起
    • void* p = std::aligned_alloc(64, size);
    • T* p = new(std::align_val_t(64)) T;
  • POSIX / Windows API
    • POSIX：posix_memalign(&p, 64, size);
    • Windows：void* p = _aligned_malloc(size, 64);
  • 释放
    • 与之配套使用 std::free、operator delete(p, std::align_val_t) 或 _aligned_free

C++的内存分区#

  • C++ 的内存通常可以划分为代码段（存放程序指令）、全局/静态区（存放全局变量和静态变量）、常量区（存放字符串字面量和常量）、堆区（动态分配内存）和栈区（函数调用时的局部变量和返回地址）。

堆内存和栈内存#

  • 栈内存：由编译器自动分配和释放，存储函数局部变量和调用信息，容量有限且速度快。
  • 堆内存：由程序员通过new/malloc显式分配和释放，适合管理大块或动态生命周期的不确定数据，但分配和释放成本更高。在需要动态扩展、可调整大小的数据容器（如std::vector）内部也使用堆分配。

指针和引用的区别#

  • 指针是一个存储地址的变量，可以指向不同对象，也可以为空（nullptr）。
  • 引用是某个对象的别名，定义时必须初始化且之后不可修改，始终引用同一个对象。

使用引用的场景：

  • 函数参数/返回值，且对象一定存在（如 void func(const std::string& s)）
  • 操作符重载（如 operator[] 返回引用以支持赋值）

使用指针的场景：

  • 对象可能不存在，需要用 nullptr 表示"无"
  • 需要在运行时改变所指对象（如链表节点 next）
  • 管理动态内存或与 C 接口交互

64位应用能在32位机器上运行吗？反之呢？#

场景 结论
64位应用 → 32位机器 ❌ 不能
32位应用 → 64位机器 ✅ 通常可以

64位不能跑在32位上：64位程序使用 rax/rbx 等64位寄存器和 REX 前缀指令，32位 CPU 无法正确解码；32位 OS 无法建立64位页表和地址空间。硬件 + OS 双重不兼容。

32位能跑在64位上：

  • 硬件层：x86-64 CPU 支持兼容模式，通过段描述符 L 位切换，L=0 时行为与真正32位完全一致
  • OS层：Windows 提供 WOW64 层将32位调用 thunk 到64位内核；Linux 通过 ia32 独立系统调用入口支持

限制：32位进程在64位机器上单进程内存上限仍是 4GB，指针仍为 4 字节。

面向对象和继承#

struct和class区别#

struct默认成员和继承都是public，class默认成员和继承都是private。

C++面向对象，封装，继承，多态；面向对象有什么好处？#

  1. 面向对象（OOP） 是一种编程范式，通过“类”和“对象”组织代码，将数据与操作数据的函数捆绑在一起。C++ 支持类（class/struct）、对象实例化和成员访问，是典型的面向对象语言。
  2. 封装（Encapsulation） 把数据（成员变量）和对数据的操作（成员函数）放在同一个类里，并通过访问控制（public/protected/private）隐藏内部实现细节，防止外部直接修改，从而提高安全性和可维护性。
  3. 继承（Inheritance） 允许一个新类（派生类）复用已有类（基类）的接口和实现，通过 class Derived : public Base，实现代码重用和接口扩展；派生类可重写（override）基类虚函数来定制行为。
  4. 多态（Polymorphism） 分为编译时多态（重载、模板）和运行时多态（虚函数）。运行时多态通过基类指针/引用调用虚函数，运行时绑定到最派生类的实现，实现同一接口多种行为。
  5. 面向对象的好处
    • 高内聚低耦合：模块边界清晰，易于维护和测试。
    • 代码复用：继承与组合减少重复，实现“写一次，用多处”。
    • 易扩展：通过派生和虚函数添加新功能，不改动原有代码。
    • 可建模现实世界：对象映射现实实体，设计更直观。

虚函数，虚函数表，虚函数表指针如何实现。虚表和虚函数表指针存放在什么位置？#

  • 虚函数（virtual function） 在类中用 virtual 修饰的成员函数，表示该函数支持运行时多态：通过基类指针或引用调用时，会根据对象的实际类型调用最派生类的实现。
  • 虚函数表（vtable） 编译器为每个包含虚函数的类生成一张“虚函数表”，本质上是一个函数指针数组，表中每个槽对应一个虚函数的地址。若子类重写了某个虚函数，会在其 vtable 中替换相应的函数指针。
  • 虚函数表指针（vptr） 每个多态对象实例的内存布局前端（通常是对象起始地址处）会隐式地多出一个指针成员，称为 vptr。这个指针在构造函数中被初始化，指向该对象所属类的 vtable。
  • 实现与存放位置
    1. vtable：编译时生成，通常存放在可执行文件或动态库的只读数据段（如 .rodata）。各个类只有一份静态 vtable。
    2. vptr：每个对象实例独有，存放在对象内存的起始位置（比如偏移 0），由编译器在构造时写入相应的 vtable 地址。

这样，对象在运行时通过其 vptr 找到对应的 vtable，再通过表中函数指针实现动态绑定调用。

this指针#

  • this指针：在非静态成员函数内部指向调用该函数的对象本身，允许访问对象成员并支持返回对象引用以链式调用；

开闭原则：#

软件实体（类、模块、函数等）应该对扩展开放，对修改封闭。

重载和重写#

  • 函数重载（Overloading）：在同一作用域内定义多个同名函数，参数列表不同，编译器在编译期根据实参类型决定调用哪个。
  • 函数重写（Override，也称覆盖）：派生类重新定义与基类中同名同签名的虚函数，调用时通过基类指针或引用在运行期动态绑定执行派生类版本；

使用右值参数的情形#

  1. 普通（非模板）类型
1

void f(std::string&& s);
  • 这里的 && 就是右值引用。
  • 只能接收右值（比如 f("hi")），不能接收左值变量（除非 std::move）。
  1. 模板参数推导的情况
1
2

template <typename T>
void f(T&& x);

这里的 T&& 不是单纯的右值引用，而是 转发引用（forwarding reference / universal reference）。

特点：

  • 如果传递右值，T 推导为原始类型（例如 int），x 类型是 int&&。
  • 如果传递左值，T 推导为左值引用（例如 int&），x 类型是 int& &&，会折叠成 int&。 这就是 引用折叠规则（& && -> &, && & -> &, && && -> &&）。

用途：这种写法配合 std::forward 可以写出完美转发的函数，把参数原封不动地转发到下游函数里。

  1. 什么时候要用 &&？

  • 你需要完美转发时： 比如写一个包装器函数，不想损失参数的左值/右值属性：

    1
2
3
4

    template <typename F, typename... Args>
auto call(F&& f, Args&&... args) {
    return std::forward<F>(f)(std::forward<Args>(args)...);
}

    这里 Args&&... 必须用 &&，否则没法正确保持“原本传的是左值还是右值”。

  • 你需要接收并“窃取”资源时： 如果你写的类就是要显式接收右值，比如移动构造/移动赋值：

    1

    MyClass(MyClass&& other);  // 典型移动构造函数

  • 你只想接收右值，避免拷贝： 如果函数逻辑要求只能绑定到右值（比如独占资源），也需要用 &&：

    1

    void setData(std::vector<int>&& v) { data = std::move(v); }
  1. 不要用 && 的情况
  • 如果你只是想“读参数”，用 const T& 就够了，效率高而且能接收左值和右值。
  • 如果你只关心拷贝而不想区分左右值，用值传递 T 也行（编译器会优化移动/拷贝）。
  • 如果不需要转发（比如观察者模式回调接口），没必要写成 Args&&...，写成 const Args&... 更直观。

// -------- UniquePtr --------
template<typename T>
class UniquePtr {
    T* ptr;
public:
    explicit UniquePtr(T* p = nullptr) : ptr(p) {}
    ~UniquePtr() { delete ptr; }

    // 禁止拷贝
    UniquePtr(const UniquePtr&) = delete;
    UniquePtr& operator=(const UniquePtr&) = delete;

    // 允许移动
    UniquePtr(UniquePtr&& other) noexcept : ptr(other.ptr) { other.ptr = nullptr; }
    UniquePtr& operator=(UniquePtr&& other) noexcept {
        if (this != &other) { delete ptr; ptr = other.ptr; other.ptr = nullptr; }
        return *this;
    }

    T* operator->() const { return ptr; }
    T& operator*()  const { return *ptr; }
};


// -------- 引用计数控制块 --------
struct ControlBlock {
    int shared_count = 1;
    int weak_count   = 0;
};


// -------- SharedPtr --------
template<typename T>
class SharedPtr {
    T*            ptr;
    ControlBlock* cb;

    void release() {
        if (!cb) return;
        if (--cb->shared_count == 0) {
            delete ptr;
            ptr = nullptr;
            if (cb->weak_count == 0) delete cb;
        }
    }
public:
    explicit SharedPtr(T* p = nullptr)
        : ptr(p), cb(p ? new ControlBlock() : nullptr) {}
    ~SharedPtr() { release(); }

    SharedPtr(const SharedPtr& other) : ptr(other.ptr), cb(other.cb) {
        if (cb) ++cb->shared_count;
    }
    SharedPtr& operator=(const SharedPtr& other) {
        if (this != &other) { release(); ptr = other.ptr; cb = other.cb; if (cb) ++cb->shared_count; }
        return *this;
    }

    int use_count() const { return cb ? cb->shared_count : 0; }
    T* operator->() const { return ptr; }
    T& operator*()  const { return *ptr; }

    template<typename U> friend class WeakPtr;
};


// -------- WeakPtr --------
template<typename T>
class WeakPtr {
    T*            ptr;
    ControlBlock* cb;
public:
    WeakPtr() : ptr(nullptr), cb(nullptr) {}
    WeakPtr(const SharedPtr<T>& sp) : ptr(sp.ptr), cb(sp.cb) {
        if (cb) ++cb->weak_count;
    }
    ~WeakPtr() {
        if (cb && --cb->weak_count == 0 && cb->shared_count == 0) delete cb;
    }

    bool expired() const { return !cb || cb->shared_count == 0; }

    SharedPtr<T> lock() const {
        if (expired()) return SharedPtr<T>();
        // 直接复用已有控制块
        SharedPtr<T> sp;
        sp.ptr = ptr; sp.cb = cb; ++cb->shared_count;
        return sp;
    }
};

读写锁（读者/写者问题）#

读写锁（Readers–Writer Lock，RWLock）是一种同步原语：

  • 读（共享）：允许多个线程同时获取“共享锁”并并发读取；
  • 写（独占）：写操作必须获取“独占锁”，期间阻塞所有读写。

好处：读多写少的场景里，大量读线程不必互相等待，吞吐量更高。 注意：实现策略不同会影响饥饿和公平性（偏向读者/偏向写者/公平）。 先用标准库（推荐，C++17+）

C++17 提供 std::shared_mutex；配合 std::shared_lock（读）与 std::unique_lock（写）。

#include <mutex>
#include <condition_variable>

class RWLock {
public:
    void lock_shared() {                    // 读锁
        std::unique_lock<std::mutex> lk(m_);
        readers_q_.wait(lk, [&]{
            return active_writers_ == 0 && waiting_writers_ == 0;
        });
        ++active_readers_;
    }

    void unlock_shared() {                  // 解读锁
        std::unique_lock<std::mutex> lk(m_);
        if (--active_readers_ == 0) {
            // 若没有读者了，优先唤醒写者
            writers_q_.notify_one();
        }
    }

    void lock() {                           // 写锁
        std::unique_lock<std::mutex> lk(m_);
        ++waiting_writers_;
        writers_q_.wait(lk, [&]{
            return active_writers_ == 0 && active_readers_ == 0;
        });
        --waiting_writers_;
        active_writers_ = 1;
    }

    void unlock() {                         // 解写锁
        std::unique_lock<std::mutex> lk(m_);
        active_writers_ = 0;
        if (waiting_writers_ > 0) {
            writers_q_.notify_one();        // 继续让写者优先
        } else {
            readers_q_.notify_all();        // 没有写者在等，放行所有读者
        }
    }

private:
    std::mutex m_;
    std::condition_variable readers_q_;
    std::condition_variable writers_q_;
    int active_readers_ = 0;
    int active_writers_ = 0;   // 0 或 1
    int waiting_writers_ = 0;
};

// 简单 RAII 守卫（可选）
struct ReadGuard {
    RWLock& l; explicit ReadGuard(RWLock& x):l(x){ l.lock_shared(); }
    ~ReadGuard(){ l.unlock_shared(); }
};
struct WriteGuard {
    RWLock& l; explicit WriteGuard(RWLock& x):l(x){ l.lock(); }
    ~WriteGuard(){ l.unlock(); }
};

C++ 常用锁有哪些？#

锁类型 特点 适用场景
std::mutex 基础互斥，竞争时走内核 futex 通用临界区
std::recursive_mutex 同线程可重入，有引用计数 递归函数持锁调用
std::timed_mutex try_lock_for/until，超时放弃 避免永久阻塞
std::shared_mutex 读共享/写独占（C++17） 读多写少（缓存/配置）
自旋锁（手动实现） atomic_flag 忙等，无内核切换 极短临界区、内核/中断

锁包装器（RAII）：

  • lock_guard：简单 RAII，不可手动解锁
  • unique_lock：可延迟加锁、手动解锁，条件变量必须用它（wait 需临时释放锁）
  • shared_lock：读锁 RAII 包装
  • scoped_lock（C++17）：原子获取多个 mutex，防死锁

自旋锁 vs mutex：自旋锁无内核切换但 CPU 空转，适合临界区只有几条指令的场景；mutex 竞争时需用户态→内核态切换，适合临界区较长的场景。

template<typename T>
class StableVector {
    static constexpr size_t CHUNK_SIZE = 8;

    std::vector<T*> chunks_;   // 每个元素是一块定长数组
    size_t size_ = 0;

public:
    ~StableVector() {
        for (size_t i = 0; i < chunks_.size(); ++i)
            delete[] chunks_[i];
    }

    void push_back(const T& val) {
        if (size_ % CHUNK_SIZE == 0)
            chunks_.push_back(new T[CHUNK_SIZE]);  // 分配新 chunk，不移动旧数据
        chunks_[size_ / CHUNK_SIZE][size_ % CHUNK_SIZE] = val;
        ++size_;
    }

    T& operator[](size_t idx) {
        return chunks_[idx / CHUNK_SIZE][idx % CHUNK_SIZE];
    }

    size_t size() const { return size_; }
};

std::vector 移动语义#

要让 std::vector<T> 在扩容/重新分配时高效“搬家”，关键是让元素类型 T 可移动且最好是 noexcept 可移动。

你需要为 T 实现：

  1. 移动构造函数 T(T&&) noexcept
  2. 移动赋值运算符 T& operator=(T&&) noexcept

为啥要 noexcept？ vector 在搬迁元素时会用 std::move_if_noexcept。如果 T 的移动可能抛异常，而拷贝不抛，vector 会退回用拷贝，性能就差了；若移动被标记为 noexcept，就能大胆用移动，显著更快。

    T(const T& other) : h(clone(other.h)) {}

        if (this != &other) { release(h); h = clone(other.h); }
        return *this;

            h = other.h;
            other.h = {};
        }
        return *this;
    }

  • 若能做到 trivially moveable（聚合、无自定义析构等），编译器还能做更激进的优化，但通常只需确保 noexcept 移动就足够让 vector 高效搬迁。

组合和继承的区别，什么时候用哪种?#

  • 本质区别

    • 继承（Inheritance）：子类“是一个”基类（is‑a），自动获得基类的接口和实现，支持运行时多态。
    • 组合（Composition）：一个类“拥有”另一个类（has‑a），通过成员变量或指针持有，使用时通过委托调用其接口。

  • 存取耦合度

    • 继承：耦合度高，强依赖基类；父类改动会影响所有子类。
    • 组合：耦合度低，只在需要时暴露接口；可在运行时替换或 mock 成员对象。

  • 何时用继承

    1. 明确的 is‑a 语义：class Car : public Vehicle。
    2. 需要复用父类实现并通过基类指针/引用做 多态 调用。
    3. 类层次稳定，不会频繁变更父类行为或接口。

  • 何时用组合

    1. 表示 has‑a 关系：class Car { Engine engine; }。
    2. 希望更灵活地 替换 或 扩展 部件（可在运行时注入不同 Engine 实现）。
    3. 避免深层次继承带来的脆弱基类问题，更符合“组合优于继承”的设计原则（开闭原则）。

单例模式#

单例模式是一种确保一个类在整个程序运行期间只有唯一实例，并提供全局访问点的设计模式。

它的好处主要有三个方面：

第一，控制全局唯一性，避免重复创建浪费资源；

第二，提供统一的访问接口，方便不同模块共享状态；

第三，延长对象生命周期，适合跨系统或跨模块的长期服务。

在游戏开发中，单例常用于全局管理类，例如配置管理器、资源加载器、输入管理器、全局事件系统等，这些模块需要在多个子系统中被频繁访问且保持一致状态。

懒汉模式是在第一次调用获取实例方法时才创建对象，优点是延迟加载、节省启动资源，但多线程下需要额外的同步机制保证安全；

饿汉模式是在程序启动时就创建实例，优点是实现简单且天然线程安全，但可能会在实例不需要时浪费内存或初始化时间。

  using ObsSPtr = shared_ptr<IObserver<Event>>;
  using ObsWPtr = weak_ptr<IObserver<Event>>;

  void detach(const ObsSPtr& o) {
    Obs* p = o.get();
    detach(p);
  }
  void detach(const Obs* p) {
    observers_.erase(remove_if(observers_.begin(), observers_.end(),
                               [&](const ObsWPtr& w) {
                                 auto sp = w.lock();

                     observers_.end());

    observers_.erase(remove_if(observers_.begin(), observers_.end(),
                               [](const ObsWPtr& w) { return w.expired(); }),

      if (auto sp = w.lock()) {
        sp->on_notify(e);
      }
    }
  }

  vector<ObsWPtr> observers_;

单例和观察者的特点和优缺点#

  1. 使用场景

  • 全局唯一对象的管理：当系统中需要唯一实例来协调全局行为时，用单例最合适。

    • 游戏中常见：

      • 配置管理器（ConfigManager，加载全局配置文件）
      • 日志系统（Logger，全局唯一日志输出入口）
      • 资源管理器（AssetManager，统一资源加载与缓存）
      • 网络会话管理器（NetworkSessionManager，管理 socket 连接）

  • 避免重复实例化：当对象构造成本高、全局复用时，单例能节省内存和初始化开销。

  1. 缺点和局限
    1. 全局状态带来的隐藏依赖
      • 任何地方都能访问单例，容易形成“隐形耦合”，调试和维护困难。
      • 代码可读性降低 → 谁修改了单例？在哪里被使用？ 不透明。
    2. 不利于单元测试
      • 测试时难以模拟或替换单例对象，导致测试隔离性差。
    3. 生命周期难以管理
      • 单例通常在第一次使用时构造，销毁时机不易控制；特别在多线程和程序退出阶段容易出问题。
    4. 违背“开闭原则”
      • 单例一旦设计好，全局只能一个实例，不易扩展成多实例版本。

二、观察者模式（Observer Pattern）

  1. 使用场景
  • 一对多的通知机制：当一个对象（Subject）状态发生变化时，自动通知多个依赖它的对象（Observers）。
    • 游戏和客户端常见：
      • UI事件系统：按钮点击时，通知所有注册的回调函数。
      • 游戏事件广播：角色死亡 → UI更新血条、播放动画、结算系统处理奖励。
      • 数据驱动更新：配置或数据模型更新 → 界面自动刷新。
      • 网络事件处理：收到服务端消息，通知所有监听该消息的系统。
  1. 缺点和局限
    1. 依赖链复杂，调试困难
      • 一个事件可能通知很多观察者 → 谁在监听？谁收到了消息？不直观。
      • 如果观察者多，触发一次事件可能导致大量回调，难以追踪问题。
    2. 性能问题
      • 如果观察者很多，频繁通知会带来额外的性能开销。
    3. 可能造成内存泄漏
      • 观察者没有及时解除订阅（detach/unsubscribe），导致对象无法释放。
    4. 过度使用会降低可维护性
      • 如果系统中过多事件依赖 Observer，逻辑分散，程序执行路径不清晰。

三、对比总结

模式 解决的问题 使用场景 缺点 / 局限
单例模式 保证一个类只有一个实例，并提供全局访问点 日志、配置、网络管理、资源缓存等需要唯一对象 全局状态耦合、不利于测试、生命周期难管理
观察者模式 建立对象间的一对多依赖关系，状态变化时自动通知 UI事件、游戏事件广播、数据驱动UI刷新 调试困难、性能消耗、内存泄漏风险

class MyString {
    std::unique_ptr<char[]> buf_;
    size_t len_ = 0;
    size_t cap_ = 0; // 不含 '\0' 的有效容量

    void ensure_capacity(size_t need) {
        if (need <= cap_) return;
        size_t newCap = std::max(need, cap_ ? cap_ * 2 : size_t(16));
        auto nb = std::make_unique<char[]>(newCap + 1);
        if (buf_) std::memcpy(nb.get(), buf_.get(), len_);
        nb[len_] = '\0';
        buf_ = std::move(nb);
        cap_ = newCap;
    }

public:
    // 构造/析构
    MyString() = default;
    MyString(const char* s) {
        size_t n = s ? std::strlen(s) : 0;
        cap_ = n;
        buf_ = std::make_unique<char[]>(cap_ + 1);
        std::memcpy(buf_.get(), s, n);
        len_ = n; buf_[len_] = '\0';
    }
    MyString(const MyString& o) {
        cap_ = o.len_;
        buf_ = std::make_unique<char[]>(cap_ + 1);
        std::memcpy(buf_.get(), o.buf_.get(), o.len_ + 1);
        len_ = o.len_;
    }
    MyString(MyString&& o) noexcept
        : buf_(std::move(o.buf_)), len_(o.len_), cap_(o.cap_) { o.len_ = o.cap_ = 0; }

    MyString& operator=(const MyString& o) {
        if (this == &o) return *this;
        cap_ = o.len_;
        auto nb = std::make_unique<char[]>(cap_ + 1);
        std::memcpy(nb.get(), o.buf_.get(), o.len_ + 1);
        buf_ = std::move(nb);
        len_ = o.len_;
        return *this;
    }
    MyString& operator=(MyString&& o) noexcept {
        if (this == &o) return *this;
        buf_ = std::move(o.buf_);
        len_ = o.len_; cap_ = o.cap_;
        o.len_ = o.cap_ = 0;
        return *this;
    }

    // 基本接口
    size_t size() const noexcept { return len_; }
    bool empty() const noexcept { return len_ == 0; }
    const char* c_str() const noexcept { return buf_ ? buf_.get() : ""; }

    char& operator[](size_t i) { assert(i < len_); return buf_[i]; }
    const char& operator[](size_t i) const { assert(i < len_); return buf_[i]; }

    void clear() noexcept { if (buf_) buf_[0] = '\0'; len_ = 0; }
    void reserve(size_t n) { ensure_capacity(n); }

    // 追加
    MyString& append(const char* s, size_t n) {
        ensure_capacity(len_ + n);
        std::memcpy(buf_.get() + len_, s, n);
        len_ += n; buf_[len_] = '\0';
        return *this;
    }
    MyString& append(const char* s) { return append(s, std::strlen(s)); }
    MyString& append(const MyString& o) { return append(o.c_str(), o.size()); }
    MyString& push_back(char c) { ensure_capacity(len_ + 1); buf_[len_++] = c; buf_[len_] = '\0'; return *this; }

    // 友元：拼接
    friend MyString operator+(const MyString& a, const MyString& b) {
        MyString r; r.reserve(a.len_ + b.len_);
        r.append(a.c_str(), a.len_).append(b.c_str(), b.len_);
        return r;
    }
};

#include <algorithm>
#include <cstddef>
#include <utility>

class Buffer {
public:
    // 构造：分配 n 个 int；默认 n=0 不分配
    explicit Buffer(std::size_t n = 0)
        : n_(n), data_(n ? new int[n]() : nullptr) {}

    // 析构：释放资源
    ~Buffer() {
        delete[] data_;
    }

    // 拷贝构造（深拷贝）：为自己分配新内存并拷贝元素
    Buffer(const Buffer& other)
        : n_(other.n_), data_(other.n_ ? new int[other.n_] : nullptr) {
        if (data_) {
            std::copy(other.data_, other.data_ + n_, data_);
        }
    }

    // 移动构造（noexcept）：窃取指针并置空来源
    Buffer(Buffer&& other) noexcept
        : n_(other.n_), data_(other.data_) {
        other.n_ = 0;
        other.data_ = nullptr;
    }

    // 拷贝赋值：强异常安全（copy-and-swap）
    Buffer& operator=(const Buffer& rhs) {
        if (this != &rhs) {
            Buffer tmp(rhs);     // 可能抛异常，但此时 *this 未改动
            swap(tmp);           // 成功后 tmp 的旧资源在析构中释放
        }
        return *this;
    }

    // 移动赋值（noexcept）：释放旧资源，再窃取 rhs 的资源
    Buffer& operator=(Buffer&& rhs) noexcept {
        if (this != &rhs) {             // 自赋值保护（包含自移动）
            delete[] data_;             // 释放自己原本资源（避免泄漏）
            n_ = rhs.n_;
            data_ = rhs.data_;
            rhs.n_ = 0;                 // 置空来源，避免双删
            rhs.data_ = nullptr;
        }
        return *this;
    }

    // 交换（供 copy-and-swap 使用）
    void swap(Buffer& other) noexcept {
        std::swap(n_, other.n_);
        std::swap(data_, other.data_);
    }

    // 简单访问接口
    std::size_t size() const noexcept { return n_; }
    int* data() noexcept { return data_; }
    const int* data() const noexcept { return data_; }

private:
    std::size_t n_{0};
    int* data_{nullptr};
};

设计大文件记事本#

面试题：设计一个高性能记事本#

Windows 记事本慢的根本原因是打开文件时一次性将全部内容读入内存。改进方案围绕三个核心点：

一、快速打开：懒加载 + 行索引#

打开文件时不读内容，只做一次顺序扫描，建立行号 → 字节偏移的索引表。之后滚动到哪里，才用 seek + read 读那几行。

配合虚拟滚动，屏幕上永远只渲染可见的几十行，无论文件多大，内存占用都极低。

二、高效编辑：Piece Table#

不直接修改原始文本，而是维护一个piece 链表，每个 piece 指向原始文件或新增缓冲区的某段区间。插入/删除只需拆分或合并链表节点，不移动任何实际数据。

1
2

插入 "hello" 前：[ (original, 0, 100) ]
插入 "hello" 后：[ (original, 0, 30), (add, 0, 5), (original, 30, 70) ]

VS Code 和 Word 均采用此方案。

三、撤销/重做：Piece Table 快照#

每次操作前将当前 piece 链表状态压栈。由于链表本身很小，快照几乎没有开销。撤销时直接恢复上一个状态即可。

预先按 8 字节对齐划分若干档位（8, 16, 24, … 256 字节），每档维护一个空闲链表。

回收：直接插回对应档位的链表头，不归还给 OS

struct FreeNode { FreeNode* next; };
FreeNode* freeLists[32];  // 对应 8B ~ 256B 共 32 个档位

一次分配/回收均为 O(1)，且无锁（单线程场景）。

二、中对象：Slab 分配器#

每个 Slab 是一大块连续内存（如 4KB），切分为等大的若干 slot，用位图记录哪些 slot 已占用：

1

[ slot0 | slot1 | slot2 | ... ]   +   bitmap: 0b00110...

同一个 Slab 内的对象紧密排列，Cache 友好，且分配时只需找位图中第一个 0 位。

三、大对象：直接系统调用#

超过 4KB 的请求直接走 malloc/free，内存池不介入，避免复杂度过高。

四、内存来源：批量向 OS 申请#

内存池本身不逐次向 OS 申请，而是每次批量申请一大块（如 1MB），内部再切分：

1

OS → Arena（1MB 大块）→ 按需切给各级分配器

减少系统调用次数，也降低碎片。

五、对象的构造与析构：Placement New#

内存池只负责分配原始内存，不负责构造对象。将内存交给调用方后，需要用 Placement New 在已有内存上手动调用构造函数：

1
2

void* mem = pool.allocate(sizeof(MyObject));
MyObject* obj = new (mem) MyObject(args...);  // Placement New：在 mem 上构造对象

回收时同样不能直接归还内存，必须手动调用析构函数，再将内存还给内存池：

1
2

obj->~MyObject();       // 手动析构，释放对象持有的资源
pool.deallocate(mem);   // 将原始内存归还内存池

这样做的原因是内存的生命周期和对象的生命周期被解耦：内存由内存池管理和复用，对象的构造/析构时机由调用方控制。

template<typename T, typename... Args>
T* MemoryPool::create(Args&&... args) {
    void* mem = allocate(sizeof(T));
    return new (mem) T(std::forward<Args>(args)...);  // 完美转发构造参数
}

template<typename T>
void MemoryPool::destroy(T* obj) {
    obj->~T();
    deallocate(obj);
}
