多人射击游戏项目介绍#

Blasters 是一款基于 Unreal Engine 5、以 C++ 为主开发的多人在线第三人称射击游戏 Demo，完整实现了生产级别的网络对战框架。以下是面试官通常最感兴趣的技术亮点：

网络架构：采用 Listen Server 模式，严格遵循服务器权威（Server Authority）原则。AGameMode 完全服务器独占，所有伤害结算、比赛状态流转均在服务器最终裁定，客户端无法伪造结果。

客户端预测：对开火、瞄准、装备武器等高频操作实现了"本地立即执行 + Server RPC 异步确认 + Multicast 广播同步"的完整预测链路，玩家操作零感知延迟。

Server-Side Rewind（延迟补偿）：自研基于历史帧回滚的服务端延迟补偿系统，使用 TDoubleLinkedList<FFramePackage> 存储最多 4 秒的碰撞盒历史，覆盖 Hitscan（射线）、Projectile（弹道模拟）、Shotgun（多弹丸）三种弹道类型，并配套了高 Ping 熔断机制。

时钟同步：实现基于 NTP 简化算法的客户端-服务器时钟校准，精确维护 ClientServerDelta，为延迟补偿的 HitTime 提供可靠基准。

武器系统：支持步枪、火箭筒、手枪、冲锋枪、霰弹枪、狙击枪、榴弹发射器七种武器，具备完整的弹药管理、换弹、拾取、抛弃逻辑，弹药以 COND_OwnerOnly 复制防止信息泄露。

多模式支持：自由乱斗与红蓝团队两种模式，通过 ABlasterGameState 同步团队分数，Team 属性驱动队友识别与模型颜色区分，ATeamsGameMode 处理组队重生逻辑。

BUFF 系统：UBuffComponent 实现血量回复、护盾回复、速度提升、跳跃提升，均有协程式 Timer 驱动，服务器结算后通过 Replication 同步 HUD 反馈。

HUD 健壮性：针对网络环境下对象初始化顺序不确定的问题，采用"懒加载 + PollInit() 轮询"双重机制，确保 HUD 在任何加入时机（开局前/中途加入）都能正确初始化。

难点一：客户端预测的实现#

整体回答#

客户端预测的核心思路是：本地玩家的操作不等待服务器确认，先在本地立即执行，同时发 Server RPC 告知服务器。这样玩家感受不到延迟，操作即时响应。项目中最典型的例子是开火和瞄准。

在 CombatComponent.cpp 的 FireHitScanWeapon() 和 FireProjectileWeapon() 中，每次开火的调用链为：

1
2
3

LocalFire(HitTarget)              ← 本地立即执行：播放动画、生成枪口特效
ServerFire(HitTarget, FireDelay)  ← Server RPC：通知服务器进行权威验证
    └─ MulticastFire(HitTarget)   ← 服务器广播：同步给所有其他客户端

LocalFire 和 MulticastFire 执行完全相同的逻辑（播放 Montage、生成弹壳等），区别仅在于执行时机。本地客户端提前执行一次预测，收到 Multicast 回来时通过动画状态检查或布尔标记来避免重复触发。

瞄准预测在 SetAiming() 里体现：先在本地直接设置 bAiming = bIsAiming，再调用 ServerSetAiming。这样 FOV 插值、移速修改等立即生效，而不是等一个完整 RTT 后才有反馈。

追问：预测出错了怎么办？客户端和服务器状态不一致时如何处理？#

以瞄准为例：bAiming 的声明是 ReplicatedUsing = OnRep_Aiming。若服务器判定该操作不合法，会将权威值复制回客户端并触发 OnRep_Aiming()，其中做了一个关键处理：

void UCombatComponent::OnRep_Aiming()
{
    if (Character && Character->IsLocallyControlled())
    {
        bAiming = bAimButtonPressed; // 用本地按键真实状态纠正，而非盲目接受服务器值
    }
}

关键在于用 bAimButtonPressed（本地记录的最新按键真实状态）而非直接接受服务器推送的值——因为在网络往返期间本地状态可能已再次变化。这是"预测 + 服务器校正"的标准模式。

更优实现：UE 官方的 CharacterMovementComponent 对移动预测采用了更完整的方案——每帧输入打上单调递增的序号（FNetworkPredictionData_Client::SavedMoves），服务器校正时携带该序号，客户端收到后**重新模拟（Replay）**序号之后的所有帧，确保每一帧状态都能被精确校正而不产生视觉跳变。本项目对武器/瞄准状态的简单校正已经足够，但若要应用于位置预测，建议参考 CMC 的 SavedMoves + PerformMovement 重放机制，或使用 UE5 的 NetworkPhysics 插件中的 FPhysicsReplicationAsyncInput 方案。

追问：开火预测里弹药数量怎么处理？#

弹药数量 CarriedAmmo 的复制条件是 COND_OwnerOnly，只复制给武器拥有者，由服务器权威管理。客户端预测开火时不会立即扣减弹药，而是等服务器处理完毕后将正确值复制回来，触发 OnRep_CarriedAmmo() 更新 HUD。

这样设计的考量是：弹药数量涉及反作弊（防止客户端伪造无限子弹），宁可 UI 有一帧 RTT 的滞后，也不能让客户端拥有弹药的写权限。而开枪的"手感"（动画、音效、准星扩散）通过本地预测已实现即时响应，两者分开处理，互不干扰。

追问：FireDelay 参数的作用是什么？#

ServerFire 携带 FireDelay 是为了服务器验证开火频率。服务器收到请求后会检查距上次开火的时间间隔是否符合该武器的射速（FireDelay = 1.f / FireRate），防止客户端通过修改本地计时器实现超速射击。这是在客户端预测框架下对服务器权威性的一个具体体现。

难点二：延迟补偿（Server-Side Rewind）的实现#

整体回答#

延迟补偿的本质问题是：客户端准星对准目标并开枪，但请求到达服务器时，目标角色已因自身操作移动到了其他位置。若服务器用当前位置做碰撞检测，玩家会体验到"明明打中了却没有伤害"。

解决方案是服务端历史帧回滚（Server-Side Rewind, SSR）：服务器为每个角色存储一段时间内的碰撞盒历史快照，收到命中请求时将碰撞盒"时光倒流"到客户端开枪时刻的位置，再做碰撞检测，以此裁定命中是否成立。

具体实现在 ULagCompensationComponent 中：

数据结构：TDoubleLinkedList<FFramePackage> FrameHistory。每个 FFramePackage 存储一个时间戳和一个 TMap<FName, FBoxInformation>，记录该帧所有骨骼碰撞盒（head、pelvis、spine 等）的 Location、Rotation、BoxExtent。

记录：TickComponent 每帧调用 SaveFramePackage()，将当前帧状态压入链表头部，并清除超过 MaxRecordTime（4 秒）的尾部旧帧，保持链表长度稳定。

回滚流程（以 Hitscan 为例）：

   - 将碰撞盒复原到当前位置

④ 命中确认后，ApplyDamage 在服务器执行，具有权威性

追问：三种武器类型的延迟补偿有什么区别？#

Hitscan（即时射线武器，如步枪）：ConfirmHit() 使用 World->LineTraceSingleByChannel，在历史位置对 ECC_HitBox 通道做一次射线检测，是最简单直接的实现。

Projectile（弹道模拟武器，如火箭筒）：ProjectileConfirmHit() 使用 UGameplayStatics::PredictProjectilePath，传入客户端上报的初始速度和起始位置，在服务器上完整模拟一次弹道轨迹，判断其是否与历史位置的碰撞盒相交。这样即使是抛物线弹道也能精确还原。

Shotgun（霰弹枪）：每次射击产生多个弹丸，ShotgunConfirmHit() 接收 TArray<FVector_NetQuantize> 命中点列表和 TArray<ABlasterCharacter*> 命中角色列表，对每个角色分别查找对应的 FramePackage，独立统计 HeadShots 和 BodyShots 数量，存入 FShotgunServerSideRewindResult，最终按弹丸数乘以单发伤害结算总伤害。

追问：MaxRecordTime 设 4 秒的依据是什么？#

这是一个存储开销与容忍延迟之间的权衡。记录时间越长，能容忍的玩家延迟越高，但内存开销也越大（每帧约 N 个角色 × M 个碰撞盒 × 帧率 × 秒数）。项目同时设置了 HighPingThreshold = 50ms（约 RTT 100ms）的高延迟熔断：Ping 超过阈值时通过 HighPingDelegate 广播，武器层订阅后可选择对该玩家禁用 SSR，退回到服务器当前位置判定。因此 4 秒的上限与高 Ping 熔断共同构成了防护体系，而不是单独作为唯一约束。

更优实现：商业项目（如 Valorant）通常会在服务器端主动测量每个客户端的 RTT，而不依赖客户端上报的 HitTime。做法是服务器记录 Server RPC 到达时间与 PlayerController 的 ExactPing，动态计算允许的最大回滚量（MaxRollback = ServerPing * 1.2，乘以一个容差系数），超出则拒绝，从根本上防止客户端伪造 HitTime 进行扩大回滚的作弊行为。

追问：碰撞盒复原时有没有并发安全问题？#

有潜在风险。在单线程游戏逻辑中，ConfirmHit 是在同一帧内完成"移位 → 检测 → 复原"的，正常情况下不会被打断。但如果同一帧内两个玩家同时对同一目标发起 ServerScoreRequest，两次回滚操作会串行执行（UE GameThread 是单线程），先执行的操作在复原之前，后执行的操作读到的是被修改过的状态——这在理论上是一个 Bug。严谨的做法是对每次回滚都使用独立的临时碰撞几何体（动态创建 UBoxComponent 或使用 FPhysicsInterface 的场景查询），不直接修改角色身上的碰撞盒，回滚完成后直接销毁临时体，完全规避状态污染问题。

难点三：开始比赛和中途加入时的各种延迟初始化#

整体回答#

这个问题分两个层面：游戏状态（比赛阶段、倒计时）的同步，以及 HUD 在网络环境下的健壮初始化。

比赛状态同步存在一个经典问题：AGameMode 只存在于服务器，客户端无法访问它。无论玩家是开局前加入还是中途加入，都需要一次主动询问才能拿到当前阶段和剩余时间。

解决方案是在 ABlasterPlayerController::BeginPlay() 里调用 ServerCheckMatchState()（Server RPC），服务器从 GameMode 读取 WarmupTime、MatchTime、CooldownTime、LevelStartingTime、MatchState，然后用 ClientJoinMidgame（Client RPC）发回客户端：

void ABlasterPlayerController::ClientJoinMidgame_Implementation(...)
{
    WarmupTime = Warmup;
    MatchTime = Match;
    LevelStartingTime = StartingTime;
    MatchState = StateOfMatch;
    CooldownTime = Cooldown;
    OnMatchStateSet(MatchState, bIsTeamsMatch); // 根据当前阶段显示正确的 HUD
}

之后客户端每帧在 Tick 里调用 SetHUDTime()，用 GetServerTime() - LevelStartingTime 推算剩余倒计时，保证时间显示与服务器一致。

HUD 延迟初始化更为棘手。网络环境下，AHUD、UCharacterOverlay、APlayerState 等对象的构造顺序并不确定，BeginPlay 时它们可能还是 nullptr。

处理方式是"懒加载 + 保底轮询“的双重机制：

所有 SetHUD* 函数开头都有如下懒加载：

1

BlasterHUD = BlasterHUD == nullptr ? Cast<ABlasterHUD>(GetHUD()) : BlasterHUD;

并在访问 Widget 子控件前进行 null 检查，避免崩溃。

ABlasterCharacter 里的 PollInit() 在 Tick 中持续轮询 BlasterPlayerController 和 BlasterPlayerState 是否已就绪，一旦就绪就完成 HUD 首次设置并停止轮询，彻底解决初始化时序问题。

追问：MatchState 是如何从服务器同步给后续加入客户端的？#

MatchState 在 ABlasterPlayerController 里声明为 ReplicatedUsing = OnRep_MatchState。对于初始连接，ClientJoinMidgame 是主动的直连通道；对于之后状态变化（如从 WaitingToStart 切换到 InProgress），Replication 系统触发 OnRep_MatchState，内部调用 HandleMatchHasStarted 或 HandleCooldown。两条路径最终汇聚到同一套 HUD 更新逻辑，保证了初始加入和运行时变化都能正确响应。

追问：为什么不直接用 GameState 同步，而要额外走一次 RPC？#

AGameState 确实会自动复制到所有客户端，ABlasterGameState 里也存着 TopScoringPlayers、RedTeamScore、BlueTeamScore 等。但有两个问题：第一，GameState 不包含 GameMode 里的配置参数（WarmupTime、MatchTime 这些是 Mode 的职责，不属于 State）；第二，玩家刚连接时 GameState 的初始复制可能还未到达，存在时序竞争。ServerCheckMatchState + ClientJoinMidgame 的一问一答模式精确控制了"连接就绪后立刻发起一次询问”，是对 Replication 时序不确定性的防御性补充。

更优实现：UE 提供了 AGameStateBase::OnRep_ReplicatedHasBegunPlay() 和 APlayerController::ReceivedPlayer() 这两个回调，时机比 BeginPlay 更晚、更可靠。对于 GameState 的配置参数问题，更规范的做法是将比赛配置（Warmup、MatchTime 等）抽成一个 UPrimaryDataAsset，通过 GameMode 在服务器初始化时写入 GameState 的 Replicated 字段，客户端监听 OnRep 回调即可，完全不需要额外的 RPC 往返。

追问：PollInit() 的轮询方式有性能问题吗？有没有更好的替代方案？#

PollInit() 在 Tick 里每帧执行一次 null 检查，代价极低（只是指针判断），且在条件满足后立即停止轮询（通过布尔标记跳过后续 Tick 逻辑），实践中可以接受。

更优实现：更优雅的方案是使用委托（Delegate）驱动替代轮询。UE 的 APlayerController 有 OnPossess 回调，APlayerState 的首次复制可以通过重写 CopyProperties 或 OnRep_Owner 来感知。具体而言，可以在 ABlasterCharacter::PossessedBy() 和 ABlasterCharacter::OnRep_PlayerState() 两个时机分别绑定初始化逻辑，彻底消除轮询，改为事件驱动。

难点四：高 Ping 情况下服务端权威与客户端信任的边界设计#

整体回答#

这是一个设计层面的难点：SSR 给了客户端很大的"权力"——它发来的命中请求，服务器会回滚历史来承认。但如果延迟极高（超过 MaxRecordTime），或者回滚量过大影响其他玩家体验，就需要限制机制。项目做了两层防护：

第一层：GetFrameToCheck 里的硬性截断

1
2
3
4
5

if (OldestHistoryTime > HitTime)
{
    // 延迟超过历史记录上限，直接拒绝
    return FFramePackage(); // 返回空，命中不予确认
}

若客户端上报的 HitTime 比历史记录中最老的帧还早，说明网络延迟已超过 MaxRecordTime，直接拒绝本次命中确认。

第二层：CheckPing + ServerReportPingStatus + HighPingDelegate

客户端每隔 CheckPingFrequency（20 秒）读取 PlayerState->GetPingInMilliseconds()，与 HighPingThreshold（50ms，即约 RTT 100ms）比较。超过阈值时通过 ServerReportPingStatus(true) 上报服务器，服务器触发 HighPingDelegate，武器层订阅后可选择对该玩家禁用 SSR，退回到服务器当前位置判定（对高延迟玩家不利，但对被攻击方公平）。

难点在于：CheckPing 只在客户端运行（HasAuthority() 时直接 return），而权威判断依赖客户端上报，存在被欺骗的可能。Demo 规模下这是可接受的权衡，但在商业项目中需要服务器自行测量 RTT。

追问：GetPingInMilliseconds() 返回的是什么？它是如何计算的？#

APlayerState::GetPingInMilliseconds() 是 UE 引擎内置属性，底层由 UNetConnection::AverageLag 驱动，引擎在每次 ACK 到达时更新该均值。它是一个估算的往返时延，以毫秒为单位，精度有限且存在平滑滞后。项目里 HighPingThreshold = 50.f，含义是单程约 50ms（即 RTT 约 100ms）时触发高延迟警告，是一个相对保守的阈值。

更优实现：商业项目中服务器应自行维护每个连接的精确 RTT。做法是在服务器的 PlayerController::Tick 里读取 Cast<UNetConnection>(Player->GetNetConnection())->AverageLag（单位秒），或更精确地通过自定义心跳包（类似本项目的时钟同步机制）在服务器侧记录发出与收到的时间差，完全不依赖客户端上报，杜绝篡改可能。

问题：UE 中怎么实现延迟（网络时延）的计算？#

整体回答#

项目实现了两套机制：自定义时钟同步（用于延迟补偿的精确 HitTime 基准）和 UE 内置 Ping 统计（用于高延迟策略判断）。

自定义时钟同步的核心是经典的 NTP 简化算法，实现在 ABlasterPlayerController 中：

① 客户端在 ReceivedPlayer()（与服务器建立连接后尽早触发）
   以及之后每隔 TimeSyncFrequency（5秒），调用：
   ServerRequestServerTime(GetWorld()->GetTimeSeconds())
   携带本地发送时的时间戳 TimeOfClientRequest

② 服务器收到后立即记录 ServerTimeOfReceipt，然后调用：
   ClientReportServerTime(TimeOfClientRequest, ServerTimeOfReceipt)

③ 客户端收到后计算：
   RoundTripTime    = GetWorld()->GetTimeSeconds() - TimeOfClientRequest
   SingleTripTime   = 0.5f * RoundTripTime          // 假设上下行对称
   CurrentServerTime = TimeServerReceivedClientRequest + SingleTripTime
   ClientServerDelta = CurrentServerTime - GetWorld()->GetTimeSeconds()

④ 之后 GetServerTime() = GetWorld()->GetTimeSeconds() + ClientServerDelta
   即本地时间 + 偏移量 = 服务器时间的实时估算

SingleTripTime 就是计算出来的单程延迟，GetServerTime() 则是延迟补偿里 HitTime 的来源——客户端开枪时记录的 HitTime = GetServerTime()，传到服务器后在历史帧中回滚，回滚目标时刻已经扣除了传输延迟，因此定位的是客户端"按下开火键那一刻"服务器的真实状态。

UE 内置 Ping：APlayerState::GetPingInMilliseconds() 由引擎自动维护，用于 UI 显示和高延迟策略触发，无需手动计算。

追问：为什么要自己实现时钟同步，用 UE 内置 Ping 不够吗？#

内置 Ping 是一个粗略的往返时延参考值，有两个根本缺陷：第一，它是定期更新的均值，不能精确反映某一时刻的偏差；第二，延迟补偿需要的不是单纯的往返时延，而是客户端时钟与服务器时钟之间的绝对偏移量 ClientServerDelta。GetServerTime() 返回的是一个"与服务器时钟校准过的本地时间"，这是 Ping 值本质上无法提供的。两者职责不同：内置 Ping 用于展示和策略控制，时钟同步用于保证延迟补偿的精确性。

追问：每 5 秒同步一次时钟，中间的误差怎么处理？#

项目中 GetServerTime() 用的是 GetWorld()->GetTimeSeconds() + ClientServerDelta，其中 GetWorld()->GetTimeSeconds() 是本地时间，每帧都在增长。只要本地时钟的走速与服务器接近（现代操作系统的时钟漂移通常在 ppm 级别，5 秒内误差 < 0.5ms），5 秒刷新一次就足够精确。如果需要更高精度（如竞技级游戏），可以缩短 TimeSyncFrequency，或采用多次采样取中位数来过滤网络抖动，这也是标准 NTP 实现的做法。

问题：哪些类和变量存储在服务器，哪些存储在本地，哪些需要复制？#

整体回答#

UE 多人游戏遵循服务器权威原则，不同类型对象的存在范围是固定的：

仅存在于服务器

AGameMode（及其子类 ABlasterGameMode、ATeamsGameMode、ALobbyGameMode）完全服务器独占，客户端无实例。比赛时间配置、玩家消除逻辑、重生逻辑全部在这里。

ULagCompensationComponent::FrameHistory：该双向链表无 Replication，ULagCompensationComponent 本身也未调用 SetIsReplicated(true)，仅在服务器 Tick 并保存历史帧，用于服务器验证命中，客户端无需感知这些数据。

ApplyDamage 调用：伤害结算的权威在服务器，只在 ServerScoreRequest_Implementation 等 Server RPC 内部执行。

仅存在于本地客户端（拥有者）

ABlasterHUD 及其所有 Widget（CharacterOverlay、Announcement、ElimAnnouncement）：HUD 只在拥有者客户端创建，GetHUD() 在服务器端返回 nullptr。

UCombatComponent 中的 CrosshairVelocityFactor、CrosshairAimFactor、HitTarget（射线检测结果）等：纯本地 UI 计算，TickComponent 里加了 Character->IsLocallyControlled() 守卫，非本地控制角色不执行。

ABlasterPlayerController 中的 ClientServerDelta、SingleTripTime：时钟偏移量只对本客户端有意义。

对象存在范围规律总结：

  • AGameMode：仅服务器
  • AGameState：服务器 + 所有客户端（自动 Replicated）
  • APlayerState：服务器 + 所有客户端（自动 Replicated）
  • APlayerController：服务器 + 拥有者客户端（其他客户端无其他玩家的 Controller 实例）
  • APawn / ACharacter：服务器 + 所有客户端（Replicated，部分属性仅 OwnerOnly）
  • AHUD：仅拥有者客户端
  • 组件是否复制由 SetIsReplicated(true) 决定：UCombatComponent 和 UBuffComponent 开启了复制；ULagCompensationComponent 未开启，仅在服务器有效

追问：APlayerController 只存在于拥有者，那其他玩家的 Controller 指针怎么访问？#

在服务器上，所有 APlayerController 都存在，服务器可以直接通过指针传递，如 GameMode->PlayerEliminated(ElimmedCharacter, VictimController, AttackerController)。

在客户端上，其他玩家的 Pawn->Controller 是 nullptr，但 Pawn->GetPlayerState() 可以访问（PlayerState 全客户端复制）。因此跨玩家的信息访问应通过 PlayerState 而非 Controller，这也是 ABlasterPlayerState 上存着 Defeats、Team 等所有人都需要看到的数据的原因。

追问：COND_OwnerOnly 和不加复制条件有什么区别？什么时候该用哪种？#

不加条件（即默认的 COND_None）表示该变量会复制给所有拥有该 Actor 引用的客户端，适合所有玩家都需要感知的状态（血量、动画状态、武器装备）。COND_OwnerOnly 只复制给该 Actor 的拥有者，适合涉及玩家私有信息的字段（弹药数、背包内容、技能冷却具体值），这样既防止信息泄露给对手，也减少了不必要的网络流量。

UE 还提供了 COND_SimulatedOnly（只给非拥有者，如第三人称动画）、COND_InitialOnly（只在 Actor 首次复制时发送一次，适合只读配置）等条件，可以根据字段的语义精细化控制复制开销。

更优实践：对于变化频繁但精度要求不高的数值（如血量百分比用于血条显示），可以结合 UPROPERTY(Replicated) + 自定义 NetSerialize（实现 FHitResult 那样的压缩序列化）或使用 FVector_NetQuantize 系列类型，在保证视觉效果的同时显著压缩带宽。

难点五：动画 Montage 在多人游戏中的网络同步策略#

整体回答#

动画 Montage 的播放本身不会自动通过 Replication 同步，PlayAnimMontage() 只在本地执行，其他客户端不会自动收到通知。项目中所有需要其他玩家看到的动画（开火、换弹、受击、死亡）都必须通过 Multicast RPC 或 RepNotify 来手动驱动。

追问：受击动画（Hit React）和死亡动画是怎么同步的？#

受击动画通过 Multicast RPC MulticastHit() 广播，所有客户端收到后播放 HitReactMontage。注意受击动画不做预测——受击是被动事件，本地客户端感知不到"自己被打了"（只有服务器的弹道判定才知道），所以必须等服务器确认后广播，没有预测的必要。

问题六：RPC 的三种类型有什么区别？项目里是怎么选择 Reliable 和 Unreliable 的？#

整体回答#

UE 的 RPC 分三种类型，各有适用场景：

Server RPC 由客户端调用、在服务器执行，用于客户端向服务器上报意图或请求权威操作，如 ServerFire、ServerSetAiming、ServerReload。

Client RPC 由服务器调用、在拥有者客户端执行，用于服务器向特定客户端推送专属信息，如 ClientJoinMidgame、ClientReportServerTime。

Multicast RPC 由服务器调用、在服务器和所有客户端执行，用于广播需要所有人感知的事件，如 MulticastFire、MulticastElim、MulticastHit。

Reliable 与 Unreliable 的选择是另一个维度：Reliable 保证到达（底层维护重传队列），Unreliable 不保证（发了就忘），两者在项目里的使用逻辑如下：

//       但如果用 Reliable 则高频受击时重传队列会爆炸式增长

追问：Reliable RPC 有什么风险？为什么不把所有 RPC 都设成 Reliable？#

Reliable RPC 底层依赖一个有序的重传队列。如果网络持续丢包，未确认的 RPC 会积压在队列中，当队列超过引擎上限（默认约 256 条，由 MaxPacketHandlerCapacity 控制）时，UE 会强制断开该连接（Close connection），玩家被踢出游戏。

因此，把高频调用（每帧或每次开火）的 RPC 设为 Reliable 是非常危险的。以 MulticastHit() 为例：如果一个玩家在 1 秒内被霰弹枪打了 30 次，产生 30 次 Reliable Multicast，在丢包环境下这 30 条全部进入重传队列，极易触发断线保护。

判断原则：

  • 涉及权威状态变更（开火、换弹、消除）→ Reliable，因为漏掉会产生逻辑错误
  • 纯视觉/音效反馈（受击动画、击打特效）→ Unreliable，偶尔丢失只是视觉瑕疵，不影响游戏逻辑
  • 高频连续数据（准星位置、角色旋转）→ Unreliable + 最新值覆盖，因为下一帧的新值会自然纠正旧值

更优实践：对于既需要可靠性又高频的场景（如技能释放序列），可以考虑用 Replicated 属性 + RepNotify 替代 Reliable Multicast RPC。属性复制天然具有可靠性（UE 的属性复制会在连接恢复后补发最新值），且引擎会自动做属性合批（多个属性变化合并进一个数据包），比大量单独的 Reliable RPC 更高效、更安全。

追问：FVector_NetQuantize 和普通 FVector 作为 RPC 参数有什么区别？#

项目里 ServerFire、ServerScoreRequest 等 RPC 的位置参数都使用了 FVector_NetQuantize 而非裸 FVector。区别在于序列化精度和带宽：

普通 FVector 每个分量序列化为 4 字节 float，三个分量共 12 字节，精度为 IEEE 754 单精度。

FVector_NetQuantize 系列是 UE 提供的压缩变体：FVector_NetQuantize 将每个分量量化为整数（精度 1cm），FVector_NetQuantize10 精度 0.1cm，FVector_NetQuantize100 精度 1m，FVector_NetQuantizeNormal 专用于单位向量（3 个分量共 6 字节）。对于射击游戏的命中点坐标，1cm 的精度完全足够，却节省了约 30%-50% 的序列化体积。

在高频 RPC 的累积效应下，这类压缩对带宽的节省是显著的，也体现了网络编程中"能省则省"的基本原则。
