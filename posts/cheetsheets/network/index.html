网络基础与协议分层#

OSI层级 TCP/IP对应层 常见协议/技术 说明
数据链路层 (Layer 2) 网络接口层 Ethernet、Wi-Fi (IEEE 802.11)、PPP、ARP 负责在同一链路上传输帧，MAC寻址。ARP 用于 IP ↔ MAC 映射。
网络层 (Layer 3) 网络层 IP (IPv4 / IPv6)、ICMP、IGMP IP 提供逻辑寻址和路由；ICMP 用于差错报告（如 ping）；IGMP 管理组播。

网络层#

IP协议首部的构成#

IP 协议首部（以 IPv4 为例）由多个字段组成，一般至少 20 字节（不含可选字段），格式如下：

  1. 版本（Version，4 bit） 指明 IP 协议版本，常见为 4（IPv4）或 6（IPv6）。
  2. 首部长度（IHL，Internet Header Length，4 bit） 表示 IP 首部的长度，单位为 4 字节。最小值为 5（即 20 字节），最大可到 60 字节。
  3. 服务类型（Type of Service / DSCP，8 bit） 原为 TOS，现在常用为 DSCP（区分服务代码点），用于服务质量（QoS）控制。
  4. 总长度（Total Length，16 bit） 整个 IP 数据报的长度（首部 + 数据），最大 65,535 字节。
  5. 标识（Identification，16 bit） 用于分片重组，标识一份 IP 数据报。
  6. 标志（Flags，3 bit） 控制分片：
    • 位 0：保留
    • 位 1：DF（Don’t Fragment，不分片）
    • 位 2：MF（More Fragments，还有分片）
  7. 片偏移（Fragment Offset，13 bit） 数据报分片在原始报文中的相对位置，单位是 8 字节。
  8. 生存时间（TTL，Time To Live，8 bit） 防止分组无限循环，每经过一个路由器减 1，为 0 时丢弃。
  9. 协议（Protocol，8 bit） 指示数据部分使用的上层协议，如 TCP(6)、UDP(17)、ICMP(1)。
  10. 首部校验和（Header Checksum，16 bit） 只校验 IP 首部是否出错，不包含数据部分。
  11. 源地址（Source Address，32 bit） 发送方 IP 地址。
  12. 目的地址（Destination Address，32 bit） 接收方 IP 地址。
  13. 可选字段（Options，可变长） 用于测试、调试或安全相关，长度不定，若存在则首部长度 > 20 字节。

总结： IP 首部字段依次为 版本、首部长度、服务类型、总长度、标识、标志、片偏移、TTL、协议、首部校验和、源地址、目的地址、可选字段。

TCP 与 UDP#

UDP的特征、优点、使用场景#

UDP（User Datagram Protocol，用户数据报协议）是一种无连接的、面向数据报的传输层协议，和 TCP 一样都位于 OSI 七层模型中的传输层，但它更加轻量级。 特点

  1. 无连接
    • 不需要在通信前建立连接，数据可以直接发送。
    • 适合一次性、小数据量的通信。
  2. 不可靠传输
    • 不保证数据一定能到达，也不保证顺序到达。
    • 没有重传机制，接收端是否收到由上层应用负责。
  3. 面向数据报
    • 发送方把数据打包成一个个独立的报文（Datagram），接收方要么完整接收，要么丢弃。
    • 不会像 TCP 那样将数据流拆分或合并。
  4. 开销小，效率高
    • 首部字段只有 8 个字节，比 TCP 的 20 字节少得多。
    • 传输延迟低，实时性更强。

优点

  1. 传输速度快，延迟低
    • 因为没有连接建立和确认过程，非常适合实时通信。
  2. 资源消耗少
    • 报文头小，没有复杂的状态维护。
  3. 支持广播和多播
    • TCP 是一对一通信，而 UDP 可以一对多，非常适合实时同步的场景。
  4. 适用于实时应用
    • 如语音通话、视频会议、网络游戏等，这些场景下数据及时到达比保证可靠更重要。

常见应用场景

  • DNS 查询
  • 视频流、语音通话（VoIP）
  • 网络游戏（实时性强，允许部分丢包）
  • 局域网广播

UDP 是一种无连接的、面向报文的传输层协议。它不保证可靠性和顺序性，但开销小、速度快，支持广播和多播，非常适合实时性要求高的场景，比如视频会议、在线游戏和 DNS 查询。

TCP的三次握手#

TCP 三次握手 (Three-Way Handshake) 流程

  1. 第一次握手：
    • 客户端 → 服务器：发送一个 SYN 报文（SYN=1，seq=x），请求建立连接。
    • 含义：客户端告诉服务器“我要建立连接，并从序号 x 开始发送数据”。
  2. 第二次握手：
    • 服务器 → 客户端：返回一个 SYN+ACK 报文（SYN=1，ACK=1，ack=x+1，seq=y）。
    • 含义：服务器确认收到了客户端的请求（ACK=x+1），并告诉客户端“我也要建立连接，从序号 y 开始发送数据”。
  3. 第三次握手：
    • 客户端 → 服务器：发送一个 ACK 报文（ACK=1，ack=y+1，seq=x+1）。
    • 含义：客户端确认收到了服务器的回应，连接正式建立。 此时，客户端和服务器都进入 ESTABLISHED 状态，可以双向传输数据。 SYN 标志位的含义
  • SYN = Synchronize sequence numbers（同步序列号）。
  • 表示“请求建立连接，并告诉对方我这边的初始序号（ISN, Initial Sequence Number）”。
  • 作用：
    1. 初始化 TCP 的序列号，用于保证数据传输有序、不重复。
    2. 是 TCP 连接建立的第一步握手信号。

简洁面试回答 TCP 采用三次握手来建立连接：

  • 第一次：客户端发送 SYN，请求连接，并携带初始序号。
  • 第二次：服务器返回 SYN+ACK，表示同意并给出自己的初始序号。
  • 第三次：客户端回复 ACK，确认服务器的序号。 客户端的 SYN 就是“同步序列号”，用来告诉服务器我要建立连接，并从这个序列号开始。

什么时候TCP序列号会产生无数据但是有一位序列号添加？#

在 TCP 中，即使没有实际数据，SYN 报文和 FIN 报文也会让序列号加 1，因为它们本身也要进入序列空间，保证被对方确认。

TCP协议的流量控制和拥塞控制#

一、TCP 的流量控制（Flow Control）

目的：保证发送方发送速率不要超过接收方的接收能力，避免接收方缓冲区溢出。

实现方式：

  • 滑动窗口机制：
    • 接收方在 TCP 报文首部的窗口大小字段（rwnd, receive window）告诉发送方自己还能接收多少数据。
    • 发送方依据接收方的 rwnd 调整发送速率。
    • 如果 rwnd=0，发送方必须停止发送（会定时发送窗口探测报文，确认接收方是否恢复）。

特点：点对点的控制，关注接收端能力。

二、TCP 的拥塞控制（Congestion Control）

目的：防止过多数据注入网络导致路由器/链路拥塞，避免丢包和时延激增。

实现方式： TCP 使用拥塞窗口 cwnd（congestion window）变量，结合接收方的窗口 rwnd，发送方实际发送窗口 = min(cwnd, rwnd)。主要算法有：

  1. 慢启动（Slow Start）：初始 cwnd 很小（通常 1 MSS），每收到一个 ACK，就将 cwnd 增大 1 MSS（指数增长）。
  2. 拥塞避免（Congestion Avoidance）：cwnd 达到阈值后，改为线性增长，每个 RTT 增加 1 MSS。
  3. 快重传（Fast Retransmit）：如果连续收到 3 个相同的 ACK，立即重传丢失的报文，而不必等超时。
  4. 快恢复（Fast Recovery）：进入快恢复时，将阈值调整为 cwnd 的一半，并让 cwnd 从阈值开始线性增长（避免回到最小值）。

特点：面向整个网络的调节，防止链路拥塞。

应用层协议#

HTTP 和 WebSocket 的主要区别#

HTTP 和 WebSocket 的主要区别在于通信模式和应用场景：

区别：

  • HTTP 是一种 请求-响应 协议，客户端必须发起请求，服务器才能返回数据，属于短连接或一次性连接；每次交互都需要重新带上完整的请求头。
  • WebSocket 则是基于 HTTP 握手建立的 全双工长连接，一旦建立，客户端和服务器都可以主动发送消息，后续通信几乎没有额外开销。

应用场景：

  • HTTP 适合：
    • 请求一次返回一次的场景，比如网页加载、表单提交、文件下载、API 接口调用。
    • 数据不需要频繁更新，交互较少的场景。
  • WebSocket 适合：
    • 需要 实时通信 的应用，比如在线游戏、聊天室、股票行情推送、协同编辑、即时消息。
    • 频繁交互、低延迟要求的场景。

一句话总结： HTTP 用于请求-响应式的资源获取，WebSocket 用于持续、实时、双向通信。

http的get和post有什么区别#

一、基本定义

  • GET：用于从服务器获取资源。
  • POST：用于向服务器提交数据（通常会产生或修改资源）。

二、语义上的区别

方法 语义 幂等性 可缓存性
GET 请求数据，不应对服务器资源产生副作用 ✅ 幂等（多次请求结果相同） ✅ 可缓存
POST 提交数据，可能修改服务器状态（新增、修改资源） ❌ 非幂等（多次请求可能产生多个结果） ❌ 默认不可缓存

三、技术上的区别

  1. 参数位置

    • GET：参数拼接在 URL 里，如

      1

      /search?keyword=book&page=2

    • POST：参数放在 请求体 (body) 里，URL 不会暴露参数。

  2. 数据长度限制

    • GET：受 URL 长度限制（不同浏览器/服务器一般 2K~8K），不适合传大量数据。
    • POST：理论上没有大小限制（受服务器配置约束），适合大数据提交。

  3. 安全性

    • GET：参数直接暴露在 URL，容易被缓存、记录日志，不适合传敏感数据（比如密码）。
    • POST：参数在请求体中，相对安全（但仍需 HTTPS 保证传输安全）。

  4. 缓存 / 书签

    • GET：可被浏览器缓存，也可以直接收藏成书签。
    • POST：不会被缓存，也不能直接收藏。

  5. 幂等性与可重复性

    • GET：多次请求不会改变服务器资源（查询、获取）。
    • POST：多次请求可能导致多次插入或修改。

四、应用场景

  • GET
    • 查询数据
    • 获取资源（页面、图片、视频、接口查询）
    • 搜索请求（?q=xxx）
  • POST
    • 提交表单（登录、注册、下单）
    • 上传文件
    • 需要修改服务器资源的操作（新增、更新）

场景题目#

为什么使用Steam系统进行联机匹配？#

直接使用 IP 地址进行联机有几个明显的局限性： 首先，绝大多数玩家处于 NAT 或路由器之后，公网 IP 可能共享且不可直接访问，这意味着点对点连接需要玩家进行端口映射等复杂操作，而这对普通玩家来说门槛很高。 其次，IP 直连缺乏稳定的匹配和会话管理机制，玩家需要手动输入 IP 地址，也没有好友系统、房间列表等体验，难以支撑大规模的公共匹配。

相比之下，Steam 提供的联机服务整合了NAT 穿透、中继服务器、加密传输以及玩家身份认证等功能，这样玩家即便在不同网络环境下也能快速建立连接，无需手动配置路由器端口。 同时，Steam 的好友系统、匹配系统、会话管理以及反作弊机制都能直接复用，节省了我们大量自研和维护的成本，并且能提供跨区稳定性和安全性更高的连接体验。 所以在商业化的多人游戏中，我们更倾向于使用 Steam 的远程联机系统，而不是直接依赖 IP 地址连接。

现代网络协议#

HTTP/2 在现代游戏中的作用#

HTTP/2 的设计目标就是提升 Web 传输性能，减少延迟、提高带宽利用率。它的很多特性在现代网络游戏（尤其是使用 HTTP/HTTPS 作为数据交换协议的游戏，例如游戏启动器、资源下载、云端交互、排行榜等）里都能直接应用。

下面是 HTTP/2 的核心特性（相比 HTTP/1.1 的改进）：

特性 说明
二进制分帧（Binary Framing Layer） 所有传输都是二进制帧，不是文本，减少解析开销，更易解析。
多路复用（Multiplexing） 在单一 TCP 连接上同时发送多个请求/响应，避免 HTTP/1.1 的“队头阻塞”问题。
首部压缩（HPACK） 通过静态字典+动态表压缩 HTTP 头，减少重复的头部传输开销。
服务器推送（Server Push） 服务器可主动推送资源到客户端缓存，无需客户端先请求。
流优先级与依赖（Stream Prioritization） 对不同流（请求）分配优先级，优化资源调度。
连接复用（Single Connection per Origin） 对同一主机复用一个 TCP/SSL 连接，减少握手延迟。
流量控制（Flow Control） 精细控制数据流速，避免堵塞。

在现代游戏里，HTTP/2 常用于资源下载、界面数据加载、云服务交互，优势主要体现在多路复用（减少延迟）、首部压缩（节省带宽）、服务器推送（减少请求次数）和流优先级（保证关键内容先到）。

Reliable UDP#

什么是 Reliable UDP？#

UDP 本身是无连接、不可靠的传输协议，不保证：

  • 数据包到达（丢包）
  • 到达顺序（乱序）
  • 不重复（重复包）

Reliable UDP 是在 UDP 之上，通过应用层逻辑选择性地补充可靠性机制，在保留 UDP 低延迟优势的同时，获得部分类似 TCP 的可靠性保证。

为什么不直接用 TCP？#

TCP UDP Reliable UDP
可靠性 ✅ 全部保证 ❌ 无 ✅ 按需保证
延迟 ❌ 高 ✅ 低 ✅ 较低
队头阻塞 ❌ 有 ✅ 无 ✅ 可避免
连接状态 有 无 可自定义
适合实时游戏 ❌ ⚠️ ✅

TCP 最大的问题是队头阻塞（Head-of-Line Blocking）：一个包丢失后，TCP 会停止交付后续所有已到达的包，等待重传。对游戏来说，一帧旧的位置数据丢了，没必要等它，直接用新数据即可。

核心机制一：序列号（Sequence Number）#

每个数据包附带一个递增的序列号，用于：

  • 检测丢包（序列号不连续）
  • 检测乱序（序列号比已接收的小）
  • 去重（已接收过的序列号丢弃）

游戏客户端开发网络技术#

客户端预测是什么？#

网络游戏中玩家输入到服务器确认之间存在 RTT 延迟（50~200ms），如果等服务器回包再更新画面，玩家会感受到明显的输入卡顿。客户端预测的做法是：不等服务器确认，直接在本地先执行玩家输入并立即渲染，同时将输入发给服务器，等服务器返回权威结果后再对账纠正。

围绕这个核心思想有三个概念：客户端预测负责本地立即响应输入；服务器调和负责收到权威结果后与本地预测对账；实体插值负责对其他玩家的位置做平滑，消除网络抖动的跳变感。

客户端预测如何实现？#

第一步，输入缓冲区。 客户端每帧将输入连同序列号发给服务器，同时在本地保存一份副本队列 pending_inputs，并立即在本地执行该输入预测结果。

第二步，本地预测执行。 客户端和服务器必须共用完全相同的 simulate(state, input) 函数（确定性逻辑），保证相同输入得到相同结果，这是整个方案的基础。

第三步，服务器调和（Reconciliation）。 服务器返回权威状态和已处理的最新输入序列号，客户端收到后：用权威状态覆盖本地状态 → 丢弃已确认的输入 → 将剩余未确认的输入重新 simulate 一遍（Re-simulation）→ 比较误差，误差小则平滑插值纠正，误差大则硬矫正。

void on_server_snapshot(ServerSnapshot snap) {
    local_state = snap.authoritative_state;

    // 丢弃已确认输入
    while (!pending_inputs.empty() &&
           pending_inputs.front().seq <= snap.last_processed_seq)
        pending_inputs.pop_front();

    // 重放未确认输入
    for (const auto& input : pending_inputs)
        local_state = simulate(local_state, input);

    // 误差修正
    float error = distance(local_state.position, render_position);
    if (error > THRESHOLD)
        render_position = lerp(render_position, local_state.position, 0.3f);
}

第四步，实体插值（其他玩家）。 其他玩家的位置来自服务器快照推送，客户端缓存历史快照，在渲染时取当前时间往前推一段（约100ms）作为插值时间点，在前后两帧快照之间做 lerp，消除抖动跳变。

值得注意的是，技能判定、扣血等强一致性逻辑不做预测，只预播表现层特效，等服务器确认后再显示真实结果，避免频繁的视觉回滚影响体验。

延迟补偿是什么？#

客户端预测解决了本地玩家的输入延迟感，但射击类游戏中还有另一个问题：玩家在客户端看到敌人在位置 A 并开枪，但由于网络延迟，这个射击请求到达服务器时，敌人在服务器上已经移动到了位置 B，导致服务器判定没有命中，与玩家的视觉体验不符。

延迟补偿的做法是：服务器保存一段时间内所有实体的历史状态快照，当收到玩家的射击请求时，将世界状态回滚到该玩家发射时刻的过去状态，在那个状态下做命中判定，判定完成后再恢复到当前状态。 本质上是让服务器站在玩家的视角去验证射击是否合理。

第一步，服务器维护历史快照环形缓冲区。 每个 Tick 记录所有实体的位置、碰撞体等状态，通常保留最近 1~2 秒的历史，用环形缓冲节省内存。

void process_shoot(ClientConnection* shooter, ShootCommand cmd) {
    // 计算回滚目标时间 = 客户端发送时刻 - 单程延迟估算
    float rewind_time = cmd.client_timestamp - (shooter->rtt / 2.0f);
    rewind_time = clamp(rewind_time, now() - MAX_REWIND, now());

    // 找到最近的历史快照插值出回滚状态
    WorldSnapshot rewound = interpolate_snapshot(rewind_time);

    // 将其他实体碰撞体临时移到历史位置
    apply_snapshot(rewound, exclude = shooter->entity_id);

    // 在回滚状态下做射线检测
    HitResult result = raycast(cmd.ray_origin, cmd.ray_direction);

    // 恢复当前状态
    restore_current_state();

    if (result.hit)
        apply_damage(result.target, shooter);
}

第四步，防作弊校验。 回滚时间不能无限制，需要设置最大回滚上限（通常 300~500ms），超出上限的请求拒绝处理，防止玩家伪造超大延迟绕过判定。同时服务器还需校验射线起点是否在合理范围内，避免客户端伪造射击位置。

实际工程中延迟补偿和客户端预测是配合使用的：本地玩家用客户端预测消除输入延迟，命中判定用延迟补偿保证视觉一致性，两者共同构成流畅射击体验的基础。

状态同步和帧同步#

状态同步是服务器作为权威，运行完整的游戏逻辑，将每帧的实体状态（位置、血量、技能CD等）广播给所有客户端，客户端只负责表现层渲染，不参与逻辑运算。客户端预测和延迟补偿都是状态同步体系下的优化手段。绝大多数现代网络游戏（FPS、MMORPG）采用这种方式。

帧同步不同步状态，只同步输入。所有客户端在本地各自运行完整的游戏逻辑，服务器只负责收集所有玩家每帧的输入并广播给所有人，只要保证每个客户端在相同帧收到相同输入，各自模拟的结果就应该完全一致。早期 RTS 游戏（星际争霸、魔兽争霸）和当前大量手游（王者荣耀）采用这种方式。

对比与选型#

两者最核心的差异在于逻辑运行在哪里：状态同步逻辑在服务器，帧同步逻辑在所有客户端。

帧同步的最大前提是确定性：所有客户端必须对相同输入产生完全相同的输出，这意味着浮点数运算、随机数种子、物理模拟步长都必须严格一致，通常需要用定点数代替浮点数来避免不同平台精度差异导致的逻辑分叉（desync）。一旦发生 desync，客户端之间状态悄悄diverge，极难排查。

帧同步的优点是带宽消耗极低（只传输入），天然支持观战和录像回放（只需保存输入序列即可完整重现对局），实现反作弊也相对简单（多数客户端投票表决）。缺点是对网络延迟敏感，一个玩家卡顿会导致所有人等待（lockstep 模式），且客户端承载了全部逻辑，反外挂难度更高。

状态同步的优点是客户端逻辑简单、服务器权威反作弊能力强、单个玩家网络波动不影响其他人。缺点是服务器计算压力大、带宽消耗高、需要额外实现客户端预测和插值来弥补延迟体验。

选型上，单位数量多、逻辑复杂、强调公平竞技（MOBA、RTS）倾向帧同步；地图大、玩家多、强调反作弊（MMO、FPS）倾向状态同步。
