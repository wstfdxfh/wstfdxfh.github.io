1. C++虚函数的实现原理是什么？虚函数表（vtable）是怎么工作的？#

高频指数：★★★★★ | 来源：腾讯/网易/米哈游/库洛 几乎必问

解答：

虚函数是C++实现运行时多态的核心机制。当基类中将某个函数声明为virtual时，编译器会为该类生成一张虚函数表（vtable），其中存放了该类所有虚函数的函数指针。

核心原理：

  • 虚函数表（vtable）：每个含有虚函数的类都有一张vtable，存储在只读数据段（.rodata）。它本质上是一个函数指针数组，里面存放着该类各虚函数的实际地址。vtable在编译期创建，与类绑定。
  • 虚表指针（vptr）：每个对象的内存布局最前面都隐藏了一个指向vtable的指针（vptr），在构造函数中被初始化。vptr与对象绑定，同一个类的不同对象共享同一张vtable。
  • 动态绑定过程：通过基类指针或引用调用虚函数时，程序在运行时通过对象的vptr找到vtable，再从vtable中查找目标虚函数的实际地址，从而调用到派生类重写后的版本。

常见追问：

  • 构造函数能否为虚函数？ 不能。因为构造时对象尚未完成初始化，vtable还未建立，无法通过vptr找到虚函数。
  • 析构函数为何要设为虚函数？ 如果通过基类指针删除派生类对象，非虚析构函数只会调用基类的析构，导致派生类资源泄漏。
  • 虚函数能否内联？ 当编译器能在编译期确定调用对象的具体类型时可以内联；表现多态性时（运行期）不可以内联。

2. C++智能指针有哪些？各自的使用场景和原理？#

高频指数：★★★★★ | 来源：腾讯/米哈游/深蓝互动 等

解答：

C++11 引入了三种智能指针来自动管理堆内存生命周期，避免内存泄漏：

类型 特点 使用场景
unique_ptr 独占所有权，不可拷贝，可移动 资源由单一所有者管理
shared_ptr 共享所有权，引用计数 多个对象共享同一资源
weak_ptr 不增加引用计数，解决循环引用 打破shared_ptr循环引用

shared_ptr 的原理： 内部维护一个控制块，包含强引用计数和弱引用计数。每次拷贝时强引用计数+1，析构时-1，当强引用计数归零时释放资源，当弱引用计数也归零时释放控制块。

常见追问：

  • shared_ptr 是否线程安全？ 引用计数的增减是原子操作（线程安全），但指向对象本身的读写不是线程安全的。
  • 循环引用举例？ A持有B的shared_ptr，B也持有A的shared_ptr，两者引用计数永远不会归零。解决方案是将其中一方改为weak_ptr。
  • UE4的智能指针？ UE4有自己的TSharedPtr、TWeakPtr、TUniquePtr体系，原理类似但与标准库独立。

3. vector和list有什么区别？各自适用什么场景？#

高频指数：★★★★★ | 来源：库洛/腾讯/米哈游 等

解答：

特性 std::vector std::list
底层结构 动态数组（连续内存） 双向链表（离散内存）
随机访问 O(1) O(n)
尾部插入/删除 均摊 O(1) O(1)
中间插入/删除 O(n)（需移动元素） O(1)（已知迭代器位置）
缓存友好性 极好（连续内存，cache命中率高） 差（节点分散，cache不友好）
内存开销 低（仅数据+少量管理信息） 高（每个节点额外存储前驱/后继指针）

适用场景：

  • vector：需要频繁随机访问、尾部增删、或数据量确定的场景。游戏中大部分场景优先选择vector。
  • list：需要在序列中间频繁插入/删除，且不需要随机访问的场景。

常见追问：

  • vector扩容机制？ 当size超过capacity时，分配新的更大内存（通常2倍），将旧元素拷贝/移动到新内存，然后释放旧内存。这个过程会导致所有迭代器失效。
  • 顺序遍历谁更快？ vector更快，因为连续内存对CPU缓存行极其友好，预取机制可以大幅减少cache miss。

4. 请描述图形渲染管线（Rendering Pipeline）的主要阶段#

高频指数：★★★★★ | 来源：几乎所有游戏公司必考

解答：

渲染管线是将三维场景数据最终转化为屏幕上二维图像的完整流程，可分为三个大阶段：

（1）应用阶段（CPU端）

由CPU负责：场景管理、可见性判断（视锥体剔除、遮挡剔除等）、设置渲染状态、提交Draw Call给GPU。

（2）几何阶段（GPU端）

  • 顶点着色器：对每个顶点执行变换（模型空间→世界空间→观察空间→裁剪空间），可进行光照计算、顶点动画等。
  • 图元装配：将顶点组装成三角形等图元。
  • 几何着色器（可选）：可以增删图元。
  • 裁剪：丢弃视锥体外的图元，裁切部分可见的图元。
  • 屏幕映射：将裁剪空间坐标通过透视除法和视口变换映射到屏幕坐标。

（3）光栅化阶段（GPU端）

  • 三角形遍历/光栅化：判断哪些像素被三角形覆盖，对顶点属性进行插值。
  • 片段/像素着色器：计算每个片段的颜色（纹理采样、光照计算等）。
  • 测试与混合：深度测试、模板测试、Alpha混合等，最终写入帧缓冲。

常见追问：

  • 坐标空间变换顺序？ 模型空间 → 世界空间(M矩阵) → 观察空间(V矩阵) → 裁剪空间(P矩阵) → NDC(透视除法) → 屏幕空间(视口变换)。
  • Early-Z是什么？ GPU在片段着色之前提前做深度测试，跳过被遮挡的片段，减少不必要的着色计算。

5. 帧同步和状态同步的区别是什么？各自的优缺点？#

高频指数：★★★★★ | 来源：腾讯/网易/深蓝 等游戏公司高频

解答：

这是网络游戏中两种主流的多人同步方案：

帧同步（Lockstep / Deterministic Lockstep）

  • 原理：所有客户端以相同的初始状态运行相同的逻辑，服务器只转发玩家的操作输入。只要逻辑完全确定性（相同输入→相同输出），各客户端的游戏状态就会保持一致。
  • 优点：带宽消耗小（只传输操作指令）；天然支持回放和战斗校验。
  • 缺点：要求逻辑严格确定性（浮点数一致性、随机数种子同步等）；一人卡顿全员等待（或需额外优化）；断线重连需要从头模拟所有帧。
  • 适用：RTS、MOBA、格斗等（如《王者荣耀》）。

状态同步（State Synchronization）

  • 原理：服务器运行核心游戏逻辑，是游戏世界的权威。客户端将操作发送到服务器，服务器计算结果后将状态广播给所有客户端。
  • 优点：对客户端逻辑一致性要求低；断线重连简单（直接同步当前状态）；防作弊能力强。
  • 缺点：带宽消耗较大（需要同步大量状态数据）；开发复杂度高（需要客户端预测、服务端回滚等机制来掩盖延迟）。
  • 适用：MMO、FPS等（如《原神》、《守望先锋》）。

常见追问：

  • 客户端预测和服务端回滚？ 客户端不等服务器响应直接执行操作（预测），收到服务器结果后如有偏差则回滚纠正（和解），提升操作手感。
  • 如何处理网络波动？ 延迟补偿、插值平滑、缓冲帧等技术。

7. TCP三次握手与四次挥手的过程是什么？为什么游戏经常使用UDP？#

高频指数：★★★★☆ | 来源：腾讯/网易/米哈游 等

解答：

三次握手（建立连接）：

  1. 客户端发送SYN报文（SYN=1, seq=x），进入SYN_SENT状态。
  2. 服务端收到后回复SYN+ACK（SYN=1, ACK=1, seq=y, ack=x+1），进入SYN_RCVD状态。
  3. 客户端回复ACK（ACK=1, seq=x+1, ack=y+1），双方进入ESTABLISHED状态。

四次挥手（断开连接）：

  1. 主动方发送FIN，进入FIN_WAIT_1。
  2. 被动方回复ACK，进入CLOSE_WAIT（主动方进入FIN_WAIT_2）。
  3. 被动方发送FIN，进入LAST_ACK。
  4. 主动方回复ACK，进入TIME_WAIT（等待2MSL后关闭），被动方收到后关闭。

为什么游戏常用UDP？

TCP的可靠传输（重传、排序）会引入额外延迟。对于实时性要求极高的游戏（FPS、MOBA），过期的数据包没有重传价值（例如，上一帧的位置信息已无意义）。因此游戏通常基于UDP自行实现可靠性控制：只对关键数据（如技能释放）做可靠传输，对位置同步等高频但容忍丢失的数据直接使用不可靠传输，从而在延迟和可靠性之间取得平衡。常见方案如KCP协议。

8. 什么是DrawCall？如何优化DrawCall？#

高频指数：★★★★☆ | 来源：腾讯/网易 Unity/UE方向

解答：

DrawCall 是CPU向GPU发出的一次绘制指令。每次DrawCall前，CPU需要设置渲染状态（材质、纹理、Shader参数等），然后提交命令给GPU。DrawCall本身的开销不在于GPU绘制，而在于CPU端的状态切换和命令提交。当DrawCall数量过多时，CPU成为瓶颈。

优化手段：

  • 批处理（Batching）：将使用相同材质的多个物体合并为一次DrawCall。
    • 静态合批：不移动的物体预先合并网格。
    • 动态合批：引擎运行时自动合并小型网格（有顶点数限制）。
    • GPU Instancing：同一网格不同位置/参数的大批量绘制。
  • 图集/纹理合并（Texture Atlas）：将多张小纹理合并为一张大纹理，使多个UI元素或物体共用同一材质。
  • 减少材质种类：尽量让场景物体共享材质。
  • 视锥体剔除（Frustum Culling）：不渲染摄像机看不到的物体。
  • 遮挡剔除（Occlusion Culling）：不渲染被其他物体完全遮挡的物体。
  • LOD（Level of Detail）：远处物体使用低精度模型，减少顶点和DrawCall。

9. 向量的点乘和叉乘在游戏开发中有哪些应用？#

高频指数：★★★★☆ | 来源：腾讯/网易/米哈游/库洛

解答：

点乘（Dot Product）：a·b = |a||b|cosθ

点乘结果是标量，反映两个向量的方向关系。

  • 判断前后关系：点乘 > 0 表示同侧（目标在前方），< 0 表示反侧（目标在后方），= 0 表示垂直。
  • 计算夹角：cosθ = (a·b) / (|a||b|)，用于FOV判定、敌人视野检测。
  • 投影：一个向量在另一个向量方向上的分量长度。
  • 光照计算：Lambert光照模型中，漫反射强度 = max(0, N·L)。

叉乘（Cross Product）：a×b = |a||b|sinθ · n

叉乘结果是向量，垂直于原来两个向量构成的平面。

  • 判断左右关系：通过叉乘结果的方向（正/负）判断目标在自身的左侧还是右侧，用于转向逻辑。
  • 计算法线：三角形两条边的叉乘得到面法线。
  • 判断点在三角形内：用叉乘法判断点是否在三条边的同一侧。
  • 计算面积：|a×b| / 2 = 三角形面积。
  • 旋转轴：用于求两个方向之间的旋转轴。

10. 进程和线程的区别是什么？游戏中多线程有哪些应用？#

高频指数：★★★★☆ | 来源：腾讯/网易/完美世界 等

解答：

对比维度 进程 线程
定义 资源分配的基本单位 CPU调度的基本单位
内存空间 独立地址空间 共享所属进程的地址空间
通信方式 管道、共享内存、消息队列等IPC 直接读写共享内存（需同步）
创建开销 大（需分配独立资源） 小
安全性 进程间互不影响 一个线程崩溃可能影响整个进程

游戏中多线程的典型应用：

  • 渲染线程：将渲染命令的生成与提交分离到独立线程，避免阻塞主逻辑。
  • 资源加载：异步加载纹理、模型、音频等资源，防止主线程卡顿。
  • 物理模拟：复杂的物理计算（碰撞检测、刚体模拟）放入独立线程。
  • 网络通信：网络收发在独立线程中进行，避免网络延迟阻塞游戏逻辑。
  • AI计算：大量AI的寻路和决策可以并行计算。

常见追问：

  • 线程同步手段？ 互斥锁（mutex）、信号量（semaphore）、条件变量、原子操作等。
  • 什么是死锁？ 两个或多个线程各持有对方所需的锁，互相等待导致永久阻塞。避免死锁的方法包括固定加锁顺序、使用trylock、设置超时等。

11. 设计模式在游戏开发中有哪些常见应用？#

高频指数：★★★★☆ | 来源：网易/腾讯/库洛/米哈游

解答：

游戏开发中最常考的几种设计模式：

单例模式（Singleton）： 确保一个类只有一个实例，并提供全局访问点。游戏中常用于管理器类，如AudioManager、GameManager。面试时常要求手写线程安全的单例（双重检查锁定 + volatile/atomic，或C++11的局部静态变量天然线程安全）。

观察者模式（Observer）： 一对多的依赖关系，当一个对象状态变化时自动通知所有依赖者。游戏中广泛用于事件系统，如角色血量变化通知UI更新。

状态模式（State）： 将对象的行为封装在不同的状态类中，根据当前状态执行不同的逻辑。典型应用是角色的动画状态机（Idle、Run、Jump、Attack等状态切换）。

工厂模式（Factory）： 定义创建对象的接口，让子类决定实例化哪个类。游戏中用于创建不同类型的敌人、道具、特效等。

组件模式（Component）： 通过组合而非继承来扩展功能，将功能拆分为独立组件挂载到实体上。这是Unity和UE引擎的核心架构思想（Entity-Component 或 Actor-Component）。

对象池模式（Object Pool）： 预先创建一批对象，需要时从池中取出使用完后归还，避免频繁创建/销毁带来的GC压力和性能开销。典型用于子弹、特效粒子、敌人等高频创建销毁的对象。

12. 什么是GC（垃圾回收）？如何在游戏中减少GC的影响？#

高频指数：★★★★☆ | 来源：Unity方向/UE方向均会问

解答：

GC（Garbage Collection） 是一种自动内存管理机制，运行时自动检测并回收不再被引用的对象所占用的内存。C#（Unity使用）和Lua等语言依赖GC管理内存。

GC的问题： GC运行时可能造成帧率波动（GC Spike），因为它需要暂停或拖慢程序执行来遍历和回收内存。对于实时游戏来说这是不可接受的。

减少GC影响的策略：

  • 对象池：复用对象而非频繁创建/销毁（子弹、特效、敌人等）。
  • 避免频繁分配临时对象：如在Update中不要每帧new对象或拼接字符串。
  • 使用值类型：在C#中优先使用struct而非class来减少堆内存分配。
  • 缓存组件引用：避免在每帧调用GetComponent等产生隐式分配的API。
  • 预分配容器：List、Dictionary等预设容量，避免运行时扩容。
  • 主动触发GC：在非关键时刻（如Loading界面）手动调用GC。

UE方向追问： UE4/UE5有自己的GC系统（标记-清除），通过UPROPERTY宏让反射系统追踪UObject的引用关系，可以通过调节GC频率、减少UObject数量等方式优化。

13. 判断一个点是否在三角形内部有哪些方法？#

高频指数：★★★★☆ | 来源：腾讯/米哈游/网易 图形学基础题

解答：

常见的三种方法：

方法一：叉乘法（同侧法）

对三角形的三条边AB、BC、CA，分别计算该边向量与该边起点到待判点P的向量的叉乘。如果三个叉乘结果的符号（方向）相同，则P在三角形内部。

1

Cross(AB, AP) 与 Cross(BC, BP) 与 Cross(CA, CP) 符号一致 → P在内部

方法二：重心坐标法

将点P表示为三角形三个顶点的加权组合：P = αA + βB + γC，其中 α + β + γ = 1。如果 α、β、γ 均在 [0, 1] 范围内，则P在三角形内。重心坐标法同时可以用于属性插值（颜色、UV、法线等），是光栅化阶段的核心。

方法三：面积法

计算三角形ABP、BCP、ACP的面积之和，若等于三角形ABC的面积，则P在内部。面积可通过叉乘的模来计算。

游戏实际应用： 光栅化中判断像素是否在三角形内、碰撞检测中的射线-三角形相交判定（Möller-Trumbore算法）等。

14. C++ 中的四种类型转换（cast）分别有什么作用？#

高频指数：★★★★☆ | 来源：腾讯/网易/完美/库洛

解答：

C++提供了四种命名的类型转换运算符，取代C风格的强制类型转换，使意图更明确、更安全：

static_cast： 编译时执行的常规类型转换。用于基本类型之间的转换（int→float）、有继承关系的指针/引用转换（向上转换安全，向下转换不做运行时检查，需要程序员保证安全性）、void*转具体类型等。

dynamic_cast： 运行时类型检查的安全向下转换。只能用于含有虚函数的多态类型。如果转换失败，指针返回nullptr，引用抛出std::bad_cast异常。底层依赖RTTI（运行时类型信息）。

const_cast： 添加或移除const/volatile限定符。这是唯一能去除const属性的转换方式。通常用于与不接受const参数的旧接口兼容。

reinterpret_cast： 最低级别的位模式重新解释，在不相关的类型之间做"硬转换"。非常不安全，几乎不进行任何检查。游戏中偶尔用于底层内存操作、序列化等。

游戏开发追问： dynamic_cast有运行时开销（需要遍历继承链），游戏中如果频繁使用会影响性能。因此UE4用自己的Cast<T>()函数（基于UObject类型系统），比标准的dynamic_cast更高效。

网络优化：

  • 减少同步数据量（差值同步、压缩、降频）。
  • 客户端预测 + 插值平滑，减少感知延迟。
  • AOI（Area of Interest）：只同步玩家附近的实体状态。

17. 堆（Heap）和栈（Stack）有什么区别？#

特性 栈（Stack） 堆（Heap）

18. 什么是内存对齐？为什么需要内存对齐？#

内存对齐（Memory Alignment）：编译器在分配结构体成员内存时，会按照对齐规则在成员之间插入填充字节（padding），使每个成员的起始地址是其大小（或指定对齐值）的整数倍。

  • 每个成员的偏移量必须是 min(成员大小, 对齐系数) 的整数倍。
  • 结构体总大小必须是最大成员对齐值的整数倍。

特性 map unordered_map

元素有序性 按key自动排序 无序

哈希表工作原理：

  1. 通过 hash 函数把 key 映射到桶（bucket）的索引。
  2. 发生哈希冲突时，同一个桶内用链表（或在节点过多时转为红黑树）串联。
  3. 当装载因子（元素数/桶数）超过阈值时触发 rehash：分配更大的桶数组，重新计算所有元素的桶位置。

常见追问：

  • rehash的代价？ 是 O(n) 的操作，游戏中如果已知容量可以 reserve 预分配，避免运行时rehash导致卡顿。
  • 自定义类型做key？ 需要提供 std::hash 特化和 operator==。
  • 什么时候用map？ 需要有序遍历、范围查询时用 map；只需要快速查找时用 unordered_map。

22. A*（A-Star）寻路算法的原理是什么？#

高频指数：★★★★★ | 来源：腾讯/网易/米哈游/吉比特 游戏方向必考

解答：

A* 是游戏中最常用的寻路算法，结合了 Dijkstra 算法的准确性和贪心搜索的效率。

核心公式： f(n) = g(n) + h(n)

  • g(n)：从起点到当前节点 n 的已知实际代价。
  • h(n)：从节点 n 到终点的估计代价（启发函数）。
  • f(n)：经过节点 n 的总估计代价。

算法流程：

  1. 将起点加入 Open List（优先队列，按 f 值排序）。
  2. 从 Open List 中取出 f 值最小的节点作为当前节点。
  3. 如果当前节点是终点，回溯路径，结束。
  4. 否则，将当前节点移入 Closed List（已访问集合）。
  5. 遍历当前节点的所有邻居：
    • 如果邻居在 Closed List 中，跳过。
    • 计算经过当前节点到达邻居的 g 值，如果更优则更新邻居的 g 值和父节点，放入 Open List。
  6. 重复步骤 2。

启发函数 h(n) 的选择：

  • 曼哈顿距离（四方向网格）：|dx| + |dy|
  • 欧几里得距离（任意方向）：sqrt(dx² + dy²)
  • 对角线距离（八方向网格）

关键性质： 只要 h(n) 不高估实际代价（即 h 是 admissible 的），A* 保证找到最短路径。

游戏中的追问：

  • 地图很大怎么办？ 可以用分层寻路（HPA*）、NavMesh、或Jump Point Search (JPS) 优化。
  • 与 Dijkstra 的关系？ h(n)=0 时 A* 退化为 Dijkstra。
  • NavMesh 的优势？ 不需要网格，在多边形之间寻路，更适合3D游戏的不规则地形。

23. 游戏中碰撞检测有哪些常见方法？如何优化？#

高频指数：★★★★★ | 来源：网易/腾讯/完美世界 等，场景题高频

解答：

碰撞检测分为两个阶段：粗检测（Broad Phase）和精检测（Narrow Phase）。

Narrow Phase 常见碰撞体：

碰撞体 原理 特点
AABB（轴对齐包围盒） 比较两个盒子在每个轴上的投影区间是否重叠 最快，但不能旋转
OBB（有向包围盒） 分离轴定理（SAT）：在15条候选分离轴上投影判断 支持旋转，更精确
球/圆碰撞 比较两球心距与半径和的大小 旋转无关，最简单
GJK 算法 通用凸体碰撞，基于闵可夫斯基差 精确，适用于任意凸形状

Broad Phase 空间优化：

暴力方法对 N 个物体需要 O(N²) 次检测，空间划分可大幅减少：

  • 四叉树（2D）/ 八叉树（3D）：将空间递归划分为4/8个子区域，只检测同一区域及相邻区域内的物体。
  • 均匀网格（Grid）：将空间分成固定大小的格子，只检测同格子和相邻格子内的物体。简单高效，适合物体大小均匀的场景。
  • BVH（层次包围体）：自底向上构建包围盒树，动态场景下增量更新效率高。物理引擎（如 Box2D、PhysX）常用。

炸弹伤害范围的经典面试题： 场景中有上万个角色，炸弹爆炸时如何快速找到范围内的角色？先用空间划分定位到可能受影响的区域，再用圆形碰撞检测精确判断距离。

24. 游戏AI中的行为树和有限状态机（FSM）有什么区别？#

高频指数：★★★★☆ | 来源：腾讯/网易/沐曈 等，AI方向必问

解答：

有限状态机（FSM）：

  • 由一组状态和状态之间的转换条件组成。
  • 在任何时刻，AI只处于一个状态（如 Idle → Patrol → Chase → Attack）。
  • 状态之间的转移通过条件触发。
  • 优点：直观简单，适合简单AI逻辑。
  • 缺点：状态多时转移关系呈爆炸式增长（N个状态最多 N×(N-1) 条转移），难以维护。

行为树（Behavior Tree）：

  • 树状结构，从根节点开始每帧 Tick，自顶向下执行。
  • 节点类型：
    • 组合节点：Sequence（依次执行，全成功才成功）、Selector（依次执行，一个成功就成功）。
    • 装饰节点：Inverter（取反）、Repeater（重复）等。
    • 叶子节点：Action（执行具体行为）、Condition（条件判断）。
  • 每个节点返回三种状态之一：Success / Failure / Running。
  • 优点：模块化、可复用、易扩展、可视化编辑友好。
  • 缺点：每帧从根遍历有一定开销，需要黑板（Blackboard）共享数据。

游戏中的选择： 简单AI（如门、开关）用 FSM 即可；复杂AI（如MOBA怪物、开放世界NPC）优先用行为树。UE5 内置了行为树 + 黑板系统。守望先锋等大型项目也使用行为树方案。

25. 什么是对象池（Object Pool）？为什么游戏中广泛使用？#

高频指数：★★★★★ | 来源：几乎所有游戏公司都会问到

解答：

对象池：预先创建一批对象放入"池"中，需要使用时从池中取出，使用完毕后归还（重置状态），而不是每次都 new/delete。

为什么游戏需要对象池：

  1. 避免频繁的堆分配/释放：new/delete 涉及系统调用和内存管理器的查找，开销大且不确定。
  2. 减少内存碎片：频繁分配释放不同大小的对象会导致碎片，对象池的内存是预先连续分配的。
  3. 避免GC卡顿（在C#/Lua等有GC的语言中）：减少对象创建就减少了GC压力。
  4. 提高 Cache 命中率：池中对象内存连续，遍历时CPU缓存更友好。

典型应用场景： 子弹、特效粒子、伤害数字飘字、小怪、UI列表项等频繁创建/销毁的游戏对象。

26. 什么是 ECS 架构？和传统 OOP 有什么区别？#

高频指数：★★★★☆ | 来源：腾讯/米哈游/沐曈 等，引擎方向常问

解答：

ECS = Entity-Component-System，是一种数据驱动的架构模式，将传统 OOP 中对象的"数据"和"行为"分离。

概念 定义
Entity（实体） 只是一个ID（轻量标识符），没有数据也没有行为
Component（组件） 纯数据容器，如 PositionComponent{x,y,z}、HealthComponent{hp}
System（系统） 纯逻辑，遍历所有拥有特定组件组合的Entity并处理，如 MovementSystem 处理所有有 Position + Velocity 的Entity

与传统 OOP 的对比：

传统 OOP ECS
对象定义 由类的继承层次决定 由挂载的Component组合决定
数据与逻辑 耦合在同一个类中 完全分离（组件存数据，系统管逻辑）
扩展方式 继承（菱形继承问题） 组合（灵活添加/移除Component）
内存布局 对象分散在堆上 同类型Component连续存储，Cache友好
典型代表 UE4 的 AActor 体系 Unity DOTS、守望先锋

ECS的优势：

  • Cache友好：同类Component紧凑排列，遍历时几乎零cache miss。
  • 易于并行：System之间如果操作的Component不重叠，可以并行执行。
  • 灵活组合：运行时动态添加/删除Component就能改变Entity的行为。

UE5 的做法： UE5 采用"混合架构"——基础是 OOP（AActor/UActorComponent），同时在 Mass Entity 框架中引入了 ECS 理念处理大规模实体。

27. 红黑树的特点是什么？为什么 std::map 用红黑树而不是AVL树？#

高频指数：★★★★☆ | 来源：腾讯/网易/字节 等

解答：

红黑树的五条性质：

  1. 每个节点是红色或黑色。
  2. 根节点是黑色。
  3. 每个叶子节点（NIL）是黑色。
  4. 红色节点的子节点必须是黑色（不能有连续的红节点）。
  5. 从任一节点到其所有后代叶子节点的简单路径上，黑色节点数量相同（黑高相同）。

这些性质保证了最长路径不超过最短路径的两倍，因此查找、插入、删除都是 O(log n)。

红黑树 vs AVL树：

红黑树 AVL树
平衡严格度 弱平衡（最长路径 ≤ 2×最短） 严格平衡（左右子树高差 ≤ 1）
查找效率 略低 略高
插入/删除 旋转次数少（最多2-3次） 旋转次数多
适用场景 插入/删除频繁 查找密集

为什么 map 选红黑树？ STL的 map 需要频繁插入/删除，红黑树在这方面的维护成本更低，是工程上的最佳折中。

游戏中的应用： map/set 底层就是红黑树，常用于管理有序数据，如事件队列、定时器、排行榜的部分实现等。

28. C++ 中如何检测和避免内存泄漏？#

高频指数：★★★★★ | 来源：几乎所有C++岗位必问

解答：

什么是内存泄漏？ 通过 new 分配的堆内存，程序不再持有其指针（或忘记 delete），导致这块内存永远无法被释放。长时间运行的游戏中内存泄漏会导致内存持续增长，最终崩溃。

常见泄漏场景：

  • new 之后忘记 delete。
  • 异常发生时跳过了 delete 语句。
  • 容器中存储裸指针，容器清空时未 delete。
  • 基类析构函数不是虚函数，通过基类指针 delete 派生类对象导致派生类部分未析构。
  • 循环引用（shared_ptr 互相持有）。

预防手段：

  • RAII原则：资源获取即初始化，用智能指针（unique_ptr/shared_ptr）管理堆内存，作用域结束自动释放。
  • 遵循 Rule of Five：自定义了析构就要自定义拷贝/移动操作。
  • 使用容器管理对象：vector<unique_ptr<T>> 而非 T* 裸指针数组。
  • 打破循环引用：用 weak_ptr。

检测工具：

  • Valgrind（Linux）：运行时检测内存泄漏和越界。
  • AddressSanitizer（ASan）：编译器插桩，高效检测泄漏、越界、use-after-free。
  • Visual Studio CRT Debug：_CrtDumpMemoryLeaks() 在程序退出时报告未释放的内存块。
  • UE5 的内存追踪：LLM（Low Level Memory tracker）和 Memreport 命令可追踪各类别的内存分配。

29. 什么是 LOD（Level of Detail）？游戏中如何使用？#

高频指数：★★★★☆ | 来源：网易/米哈游/腾讯 图形方向常问

解答：

LOD（层次细节）：根据物体与摄像机的距离（或物体在屏幕上的占比），动态切换模型/纹理的精度等级。距离近时使用高精度模型，远时切换为低精度模型，以减少渲染开销。

常见 LOD 类型：

类型 说明
Mesh LOD 为同一物体准备多套不同面数的模型（LOD0最精细，LOD1/2/3依次简化），按距离切换
Texture Mipmap 纹理预计算多个缩小版本，GPU根据距离自动采样低分辨率版本，减少显存带宽和锯齿
HLOD（Hierarchical LOD） UE5特性，远距离时将多个小物体合并为一个简化的代理网格（Proxy Mesh），大幅减少DrawCall
Nanite（UE5虚拟几何体） 自动化LOD系统，实时根据屏幕像素密度流式加载三角形集群，无需手动制作LOD

LOD切换的问题与优化：

  • 跳变（Popping）：切换瞬间模型突变，通过 Dithering（抖动过渡） 或 CrossFade 实现平滑过渡。
  • 距离阈值设置：太近切换浪费性能，太远影响画质，需要根据物体的屏幕占比来判断。

面试追问：

  • Mipmap的原理？ 每一级是上一级长宽各缩小一半的纹理，GPU根据纹理像素与屏幕像素的比率选择合适层级，多了约1/3的显存。
  • 和遮挡剔除的关系？ LOD减少单个物体的渲染量，遮挡剔除（Occlusion Culling）减少需要渲染的物体数量，两者互补。

    int cur = -1;

        history.resize(cur + 1);   // 丢弃 Redo 历史
        cmd->Execute();
        history.push_back(std::move(cmd));
        cur++;

    void Undo() { if (cur >= 0) history[cur--]->Undo(); }
    void Redo() { if (cur+1 < (int)history.size()) history[++cur]->Execute(); }
};

热重载能生效的前提：数据和逻辑分离。 技能的行为由数据（JSON）驱动，运行时读取数据执行对应动作。改数据就能改行为，不需要重新编译 C++ 代码。如果技能逻辑硬编码在 C++ 里，就只能靠 Live Coding 热补丁，而且改不了类的内存布局。

面经来源： 米哈游面经"大模型应用方面怎么做的，延迟如何"。

三个具体场景：

场景一：AI 辅助关卡布局 策划给几个关键点（出生点、Boss 区），AI 自动补全怪物分布、障碍物摆放。可用 LLM 输出结构化 JSON 配置。

36. 构建一次完整包体需要 2 小时，你怎么优化？#

面经来源： UE 面经"谈到 UBT 构建系统"；网易面经"每天生成 2T 打包数据"。

分四层回答（面试时逐层展开）：

① 增量构建（最关键）

  • 每个源文件算哈希，对比缓存，只重新处理变化的文件。
  • 需维护依赖图（DAG）：MaterialA 引用 TextureB，B 变了 A 也重建。

② 并行构建

  • 贴图压缩、模型烘焙等独立任务，用线程池并行处理。
  • 大团队可用分布式构建（类似 IncrediBuild）。

③ 构建缓存共享

  • 本地缓存：同一机器不重复处理。
  • 远程缓存：A 同事构建过的，B 直接拉取。

④ 流程优化

  • 分模块打包：日常只构建当前模块。
  • 监控看板：记录每次各环节耗时，找瓶颈。

回答要点： 先问"慢在哪一步"（定位瓶颈），再从增量→并行→缓存→流程递进。

方案二：工作线程 + 任务队列（工业级）

方案三：分帧处理（轻量，无多线程复杂度）

bool Tick() {  // 每帧调用
    int end = std::min(current + 50, total);  // 每帧处理50个

38. 什么是 AI Agent？和普通 LLM 对话有什么区别？#

面经来源： 网易面经"做智能NPC的"部门；2025 校招 Agent 高频题。

核心区别：

普通 LLM： 一问一答，你问它答，无后续动作。

AI Agent： 自主循环系统，能 感知 → 规划 → 调用工具 → 记忆 → 反思：

1
2
3
4
5

用户: "帮我查哪些怪物掉火焰宝石"
  LLM 思考 (Reasoning): 需要查配表
  → 调用工具 (Action): 搜索 drop_table WHERE item="火焰宝石"
  → 得到结果 (Observation): [火焰巨人, 熔岩龙]

39. 什么是 RAG？在游戏工具中有什么用？#

面经来源： 2025 校招高频题；阿里/字节大模型面试常考。

RAG = 检索增强生成： 在 LLM 回答之前，先从外部知识库检索相关信息，塞进 Prompt 里，让 LLM 基于真实数据回答，避免幻觉。

1
2
3
4
5
6
7
8

用户: "火系法师冷却时间是多少？"

RAG 流程:
  ① 问题 → 向量化 (Embedding)
  ② 在技能配表向量库中检索最相关条目
  ③ 找到: {烈焰风暴, 元素:火, 冷却:12秒}
  ④ 检索结果 + 原问题一起发给 LLM
  ⑤ LLM 基于真实数据回答: "冷却时间12秒"

RAG vs 微调：

RAG 微调
数据更新 改知识库即时生效 要重新训练
成本 低 高（GPU）
幻觉 有来源可溯 仍可能编造

游戏配表频繁变动，RAG 更合适。

工具中的应用：

  • 策划问答： “哪些怪掉火焰宝石？” → 从配表检索回答。
  • 文档助手： 新人问"编辑器怎么用？" → 从 Wiki 检索回答。
  • Bug 辅助： 输入报错 → 从历史 Bug 库检索解决方案。
